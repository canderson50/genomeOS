## What this changes, and why

P1 is the "what was measured" layer, and §12 says a bad value must fail the build rather than be
coerced. Both observation schemas were doing the opposite: they set `coerce=True` while declaring
the counts and date bounds as `pa.Column(int)`. Pandera coerces *before* it checks, and numpy int
casting truncates, so on `main` today:

```
an          200.5 -> ACCEPTED as 200
ac          50.7  -> ACCEPTED as 50
date_lower  3.9   -> ACCEPTED as 3
an          '200' -> ACCEPTED as 200
```

Nothing downstream can tell a stored `200` from a measured one. A binomial likelihood over a
denominator that was silently invented is not the object §7.1b describes.

**There is a second failure that the issue title does not cover, and it is the more serious one.**
The cross-field checks run on the *post-coercion* values, so:

```
ac=200.9, an=200 -> ACCEPTED as ac=200
```

A row whose allele count exceeds its allele number **passes `ac_le_an`**, because truncation cut it
down to 200 first. Truncation is not merely losing precision here — it is manufacturing conformance
to the invariant the check exists to enforce. `carriers_le_individuals` and `date_lower_le_upper`
have the same exposure. This is live in `main`.

### The fix

The eight count and date columns become pandas' nullable `Int64`. Its casting is *safe* rather than
truncating: it raises on a non-integral value, while still accepting an integral float like `200.0`
— which every adapter computing `2 * n` in floating point legitimately produces.

| input | before | after |
|---|---|---|
| `an=200.5` | accepted as `200` | refused |
| `ac=50.7` | accepted as `50` | refused |
| `date_lower=3.9` | accepted as `3` | refused |
| `ac=200.9, an=200` | **accepted as `ac=200`** | refused |
| `an=200.0` | accepted | accepted |
| `an=None` | refused | refused |

`coerce=True` stays, so nothing else in either schema moves. Column-level `coerce=False` cannot help
— schema-level coercion wins — exactly as the existing note above the boolean column records. I
verified that claim rather than inheriting it. Global `coerce=False` was the obvious alternative and
I rejected it: it makes every adapter responsible for exact dtypes and buys no extra safety here.

This is the general form of the defect fixed adapter-locally in #154/#160, where AFND's `int(n)`
truncated a fractional sample size. That fix protected one adapter; every other source still reached
a coercing schema.

## What an expert should check (`wants-expert-review`)

**Is refusal the right response to a non-integral count, or does some source legitimately report a
fractional *effective* sample size?** A weighted or design-corrected survey can, and a design effect
can produce a non-integral effective `n` that is a real quantity rather than a parsing artefact.

If such a source exists, the right answer is still not schema coercion — it is a named refusal at
ingest plus an explicit decision in that adapter about what denominator to carry, so the choice is
visible in the `IngestReport` rather than applied silently to every source at once. But *which*
sources those are is a domain judgement I should not make alone, and it is the one thing in this PR
that could be wrong in a way the tests cannot catch.

Worth a second opinion too: `200.0` is accepted as equal to `200`. I think that is right — it is the
same measurement, and refusing it would break every adapter that computes `2 * n` in floating point
— but it is the one place where this change still trusts a float.

## What I reproduced on `main`

```
an=200.5            -> ACCEPTED, stored as 200
ac=50.7             -> ACCEPTED, stored as 50
ac=200.9, an=200    -> ACCEPTED, stored as ac=200   <- passes ac_le_an

## What I confirmed about the fix

All four fractional cases refused. `an=200.0` still accepted, which matters because any adapter
computing `2 * n` in floating point produces it. `an=200.0000000001` refused, so near-integers do not
slip through either.

**It closes more than the description claims.** The body lists `an='200' -> ACCEPTED` among the
defects without saying whether strings are fixed. They largely are:

```
an='200.5'   -> refused        an='2e2'    -> refused
ac='50.7'    -> refused        an='abc'    -> refused
ac='200.9', an=200 -> refused  an='  200 ' -> refused
an='200'     -> accepted as 200
```

Only a clean integral string still coerces, which loses nothing and manufactures nothing. Worth
saying in the body, since a reader of the "before" list would reasonably assume the string case is
still open.

## The tests have teeth

I reverted each column individually and re-ran:

| Mutation | Result |
|---|---|

## The follow-up, and why it is not yours

`CPIC_COVERAGE_SCHEMA` in `genomeos/registry/curated.py` has three count columns declared the same
way in a coercing schema, and they truncate:

```

Identical shape, same class of value. Filed as #338 rather than requested here — widening a clean P1

and the general form deserves a general guard.

Nice piece of work — particularly separating the precision loss from the invariant-laundering, which
