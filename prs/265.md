## Body

## Problem and resulting behavior

A second registry build could replace coordinates while still reporting the same registry version. Registry publication now refuses an existing destination and binds each complete release to its logical tables and exact source and implementation inputs. P1 verifies the completion manifest, file bytes, schemas, and full identity before ingesting observations.

Closes #262 and advances #189 WP0. Implements Atlas design §§5–6, 12–13. The focused specification and implementation plan are committed under `docs/superpowers/`; `docs/registry-publication.md` describes the public contract and migration.

## Contract and tradeoffs

- The branch includes PR #263's explicit HGDP input boundary through `main` and now contains only the 12 immutable-publication files in its review delta.
- Full identity is `RELEASE+sha256.DIGEST`, with a complete SHA-256 digest. Logical identity and exact Parquet serialization hashes are separate; byte-exact consumers must also pin the manifest file hashes.
- `build_registry.py` requires `--release-version` and a new output path. P1 refuses unmanifested legacy directories. Rebuild from known curated inputs into a fresh directory; existing artifacts are preserved and missing provenance is never reconstructed.
- Checked public preparation and manifest operations replace private cross-module coupling. The public API maintenance obligation is covered by direct boundary tests.

The manifest appears only after both Parquet files are written, fsynced, and verified. Failed builds retain their incomplete directory for inspection. Errors after manifest commit explicitly report that publication may already be committed; no overwrite or automatic retry occurs.
