## Body

## What this adds
A third external-reference tab in the Atlas "More info" panel, next to gnomAD and dbSNP. The tab is labeled Predicted impact (AlphaGenome) and renders a reviewed, cached AVI readout per variant: Phred score, genome-wide tail rank, dominant modality, pinned model version, and a deep link to the AlphaGenome Atlas page.

Seed variant: rs334 (HbS, chr11-5227002-T-A), the same variant whose measured frequency the Atlas already maps.

## Why it fits the project
- Implements the external-info architecture from #171/#173 (design §11): allowlist entry -> validated cached JSON per variant -> panel tab -> zod contract. No new UI surface, no atlas layer, no science change.
- Keeps the measured vs inferred separation (design §4/§5). The cache payload carries a contract-level `prediction_class: "predicted_impact"` and the UI renders a "Predicted impact" tag and an explicit note: AVI is a model prediction of molecular impact, not a measured allele frequency and not a clinical classification. Predictions never qualify or disqualify a measured source.
- Immutable cache pattern matches the artifact-immutability invariant: model version and retrieval date live in the payload, so a future AlphaGenome recompute cannot silently change a cited readout.

## Review round 1
Two changes requested and one rename suggested. All three are in the latest commit.

**1. The exporter and the contract now agree on what an external lookup accepts.** A cytokine locus is typed `variant` but carries a composite id, so `_external_resources` accepted it and every check passed, while the browser contract's `normalized_variant_id` regex rejected it. That passed export and passed CI, then failed in a reader's browser at runtime. The exporter now applies the same coordinate rule, so it fails the build instead. The existing allowlist was checked first: all three external-resource entries are coordinate-shaped and the four cytokine entries declare no external resources, so the gate refuses nothing that exists today. The comment records that those loci are ineligible because their coordinates are unresolved, not for any biological reason.

**2. The per-feature attribution breakdown is removed.** DeepMind defines the AVI Score Feature Breakdown as separate from the AVI Score, and their download listing puts it under non-commercial use only, while the AVI Score itself permits commercial use. The panel was publishing the restricted half. It is gone from the payload, the contract and the card, and `NON_REDISTRIBUTABLE_ALPHAGENOME_FIELDS` refuses a cache payload that reintroduces it, so the two gates agree rather than relying on the strict object alone. The score, tail rank, dominant modality, pinned model version and deep link all stay. The verbatim terms and the reasoning are in `docs/audits/alphagenome-avi-licensing.md`. The AlphaMissense concern recorded in #193 is out of date: those predictions are CC BY 4.0, changed 2024-03-13 in `fe2dc845`.

**3. `method` separates the lookup from the provider.** The coordinate requirement is a property of the Atlas AVI lookup, which is keyed by coordinate and ref/alt, and not of AlphaGenome the model, which is sequence-to-function and could in principle score an allele carrying no coordinate. `source` stays `alphagenome` for both, `method: atlas_lookup` carries the distinction, and the static provider cross-checks it alongside the model version. One field.

## Scientific motivation (Manpreet Bola, verified run 2026-09-09)
A saturation scan of HBB intron 2 (2,547 single-letter changes, AlphaGenome AVI, checked against ClinVar via NCBI eutils) found:
- 64 changes rank in the top ~3% of predicted impact genome-wide;
- 42 of those have no clinical classification (38 never submitted to ClinVar, 4 VUS);
- the strongest unrecorded change, c.316-2A>T (Phred 40.50, top ~0.0089%), sits at the same splice-acceptor base as c.316-2A>G, a recorded cause of beta thalassemia (ClinVar 21191).

An impact readout is most useful exactly where the clinical record is thin. This PR ships the readout as an annotation that points at gaps without pretending to fill them.

Run provenance: AlphaGenome Atlas AVI values for rs334 (Phred 11.77, tail quantile 0.0665, ALPHAMISSENSE dominant) were fetched and reviewed on 2026-09-09; arithmetic and ClinVar cross-checks verified against NCBI eutils. The seed JSON is a reviewed cache, not a live API dependency.

## Superseding one ask from my review: do not add the coordinate-shape check

@manpreetbola — in my review above I asked you to enforce the coordinate shape inside `_external_resources`, so the exporter would stop disagreeing with the zod contract about `cyt:*` identifiers. **Please don't build that.** It has been replaced by something better, and I'd rather tell you now than have you spend time on the weaker version.

### What replaced it

A reviewed lookup table, `data/registry/variant_normalization.tsv`, mapping an internal `variant_id` to a normalized GRCh38 identity. The exporter now asks that registry whether a coordinate identity exists, instead of pattern-matching the identifier:

```python
if declared and normalized_identity(variant_id, variant_registry) is None:
    raise ValueError(f"...: no reviewed normalization for {variant_id}; ...")
```

**Why one gate beats two.** A regex in the exporter plus a regex in `contracts.ts` is two rules that can drift, and the drift is exactly what the review found: the Python side accepted a `cyt:*` resource that the browser then rejected at runtime. One lookup cannot disagree with itself.

**It also answers the harder question your PR raised.** The four cytokine loci are genuinely single-nucleotide changes that happen to be *named* by promoter offset, so a shape check would have excluded them permanently on a technicality. The registry lets them become eligible when someone establishes and reviews their coordinate identity — which has now been done for all four, with the rsID, the GRCh38 placement, the strand, and the citation that establishes each legacy name, each resolved from two independent resources.

### What this means for your PR

Nothing else changes. The `entity_type` gate that excludes HLA and KIR artifacts is untouched, and your AlphaGenome card is unaffected — `chr11-5227002-T-A` resolves through the registry, so it stays eligible exactly as before.

The other two review items still stand: the `top_attributions` licensing question, which is the one I'd genuinely block on, and the `closes #193` keyword burying two still-open questions.

Design and plan are in #247 and #250; the implementation is on `feat/variant-normalization-registry` and will arrive as its own PR. Sorry for the churn on this one — the right answer only became clear after your PR surfaced the underlying problem.

## The one change I am asking for: the Python and TypeScript gates disagree

A cytokine locus is typed `variant` but carries a composite id, so:

- the **exporter accepts** an AVI card for `cyt:il-6-174-c` — `normalized_variant_id == variant_id` and `entity_type == "variant"`, so every check passes;
- the **browser rejects** it, because `externalResourceSchema`'s alphagenome member requires `^chr(?:[1-9]|1[0-9]|2[0-2]|X|Y|MT)-[1-9][0-9]*-[ACGT]+-[ACGT]+$`.

So a wrong entry passes export **and passes CI**, then fails in a reader's browser at runtime. Please enforce the coordinate shape in `_external_resources` too, so the two gates agree and the failure is a build failure. The regex already exists in the contract; the exporter just needs to apply the same rule.

Worth being precise about *why* those four cytokine loci are ineligible today: they are genuinely single-nucleotide changes biologically (IL-6 −174 C>G and friends), so this is a missing-normalisation limit rather than a biological one. They plausibly become eligible once they carry resolved coordinates. A comment saying that would stop the next person reading the gate as a claim about cytokine biology.

## A naming point, because the constraint is being attached to the wrong noun

The coordinate requirement is a property of the **Atlas AVI lookup**, which is keyed by coordinate and ref/alt. It is not a property of AlphaGenome as a technology — the model is sequence-to-function, so it could in principle score an HLA allele given that allele's sequence. (Credit to @bschilder for the correction; I had collapsed the two.)

Right now the source key is `alphagenome`, which merges the lookup and the model. If model-derived scores for composite alleles ever land, they are also legitimately "AlphaGenome" yet cannot satisfy a coordinate key, and the constraint would then be pinned to the wrong thing.

Cheap to separate now, with one entry to migrate rather than many: keep `source: "alphagenome"` as the provider and add a method discriminator — an Atlas lookup versus model inference — and attach the coordinate requirement to the lookup method. That also gives Open Targets a clean home later, since it is another provider with its own method, and it keeps `prediction_class: "predicted_impact"` as the grouping it already is.

To be clear about scope: I am **not** asking for a general interpreter abstraction. `AGENTS.md` says to wait for two real consumers, and there is one. This is a field, not a framework.

## What is well built and should not change

- **No serving-path inference.** The score is a committed static payload; nothing calls an external model at request time. That is the §5 invariant respected exactly, and it is the thing most annotation features get wrong.
- **Version pinned in two places and cross-checked.** `model_version` lives in both the allowlist entry and the payload, and the exporter refuses a mismatch — with a test that asserts the refusal, not just the happy path.
- **`cache_sha256` is computed at publish time**, not copied from the allowlist, so it is tamper-evident rather than decorative.
- **Path-traversal guard** on `cache_file` (`is_absolute()` or `..` refused).
- **The contract forbids mislabelling.** `prediction_class` is a literal, and a test asserts a record fails to parse if it claims `measured`. That is the measured-versus-inferred separation enforced in the type system rather than in a convention.
- The card is tagged **Predicted impact** with an explicit note that it is neither a measured frequency nor a clinical classification.

## Licensing: I looked the terms up, and the answer is specific

Not legal advice, and worth a maintainer confirming, but the primary sources are clearer than the open question in #193 assumed. All accessed **2026-09-10**.

**Good news first: the AVI score itself is permissively licensed.** DeepMind's [AlphaGenome Services Additional Terms](https://deepmind.google.com/science/alphagenome/terms) (last modified 2026-09-08) carve the score out of the otherwise strict non-commercial regime:

> AVI Scores and other artifacts that are made available for download within the "Permissive Use Downloadable Artifact" section … **may be used for commercial use and in connection with any commercial organisations**.

The general ban is real — "The AlphaGenome Services are **only** available for use by individuals and non-commercial organizations … aren't available for any commercial entity, even if conducting non-commercial work" — but the AVI score is exempted from it, from the ML-training prohibition, and from the conspicuous-notice requirement that attaches to other Output. So storing `avi_phred` and `avi_raw_score` publicly looks fine.

**The problem is `top_attributions`.** The same terms define the attribution breakdown as a *separate artifact that is not part of the AVI Score*:

> "AVI Score" means the AlphaGenome Variant Impact score … **For clarity, the AVI Score Feature Breakdown (defined below) does not form part of AVI Score.** "AVI Score Feature Breakdown" means the breakdown showing features and inputs used to generate the AVI Score.

And DeepMind's own download listing puts `avi_feature_importances_snvs` (SHAP feature importances) under **"Downloadable artifacts for non-commercial use only"**, while `avi_scores_snvs` sits under the permissive heading.

This PR commits and publicly serves exactly that restricted artifact:

```json
"top_attributions": [
  {"feature": "ALPHAMISSENSE", "value": 0.1662},
  {"feature": "CACTUS_241_WAY", "value": 0.0318},
  {"feature": "MERGED_SPLICING", "value": 0.0281}
]
```

[The component renders it under a "Model attribution" heading](https://github.com/manpreetbola/genomeOS/blob/f57f591cdf52809b27b29c69bdc746f4f5b2b9ee/website/src/components/atlas/AlphagenomeEvidence.tsx#L54-L70), and the zod contract **requires** the array with `min(1)`, so it cannot simply be omitted per-variant.

This is the gnomAD pattern `AGENTS.md` already warns about in so many words — "gnomAD is CC0, but its bundled SpliceAI annotations are CC BY-NC" — one source, two licences, and the restricted half is the interesting-looking half. **My recommendation is to drop `top_attributions` from the payload, the contract and the card**, keeping the score, percentile, dominant modality and deep link, all of which fall inside the permissive carve-out. That loses the least defensible part of the display and the most restricted.

**One worry from #193 is stale and can be retired.** The concern about AlphaMissense being CC BY-NC-SA is out of date: [google-deepmind/alphamissense](https://github.com/google-deepmind/alphamissense) now states its predictions are CC BY 4.0, changed in commit `fe2dc845` on 2024-03-13. So the AlphaMissense contribution imposes no non-commercial restriction downstream.

**The residual question, and the one I would put to DeepMind.** The commercial carve-out is worded against "artifacts … made available for download within the *Permissive Use Downloadable Artifact* section," not unconditionally against the AVI value however obtained. This payload records `Atlas AVI, accessed 2026-09-09` — an Atlas read, not the bulk file. The low-risk path is to source scores from `avi_scores_snvs_tabix.zip` and get written confirmation at `alphagenome@google.com`, which the terms name as the contact. Cheap to do now, and it also solves refresh cadence, which was #193's second open question.

Also note the code and weights are governed separately: both repos are Apache-2.0, but the [Model Terms](https://deepmind.google.com/science/alphagenome/model-terms) put the *model parameters and general outputs* at non-commercial with **no** AVI-style exception. That matters for the sequence-model path discussed above — scoring an HLA allele with the model directly would fall under the restrictive document, not the permissive carve-out. Worth knowing before anyone builds it.
