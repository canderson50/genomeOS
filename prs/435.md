## Body

## Scientific contract

1. **Claim.** A NumPy array uploaded to a CUDA device for arithmetic qualification arrives with the same shape, dtype and bit pattern, so a refusal the core makes on NumPy (for example the noncanonical `ScaledPair` `(-0.0, +0.0, 0)`) is also made on CuPy.
2. **Measurable output and acceptance evidence.** On a real CUDA device with CuPy 14.2.0:
   - plain `cp.asarray` on a 0-D `-0.0` is recorded losing the sign bit, which reproduces #276;
   - `to_device_exact` keeps bits `0x8000000000000000` in 0-D, 1-D, 2-D and non-contiguous arrays;
   - the unchanged `count_scaled` core raises `ValueError` for every listed noncanonical pair uploaded through the helper.
3. **Component and public interface.** `genomeos.validation.device_transfer.to_device_exact(host, *, array_module)`. The array namespace is supplied by the caller, as in `count_scaled`, and CuPy is never imported. The helper uploads a 1-D buffer, reads it back, compares bytes, then reshapes on the device.
4. **Assumptions, refusals, consumers.**
   - It refuses non-NumPy inputs and object dtypes (`TypeError`).
   - It refuses any change to bytes, dtype or length on transfer (`ValueError`). Nothing is silently substituted.
   - It assumes a 1-D upload preserves bits. This is checked on every call, not just assumed.
   - The consumer is the private E1 CUDA qualification harness, which is **not** in this repository and is not changed here.

## What this changes, and why

#276 found that CuPy 14.2.0 `asarray` turns a 0-D float64 negative zero into positive zero. A harness that uploads retained NumPy evidence with plain `asarray` therefore hands the core a different input from the one recorded. The core then correctly accepts it, and the expected refusal (`refusal.first.2403.add`) never fires. This PR adds the repaired transfer as a small public helper with regression tests. The scaled-arithmetic core, `count_scaled._array`, is deliberately left unchanged, as #276 treats the core as correct.

## TL;DR

Correct, and it fails closed. I ran the CPU suite and probed it with fake array namespaces. Two optional hardening nits.

## Findings

1. **`device_transfer.py:45-47` checks the 1-D upload but not the array it returns.** After `reshape`, only shape and dtype are checked, so a namespace whose `reshape` altered bits would pass. Real CuPy reshape of a C-contiguous array is a view, so this is reasoning rather than a bug — but reading `device` back (or softening the "checked, not assumed" docstring) would close it.
2. **`:34` accepts ndarray subclasses.** A `np.ma.MaskedArray` loses its mask silently at `:38`, which contradicts "nothing is silently substituted". `type(host) is np.ndarray` would refuse it with `TypeError`.

## What I verified

16 passed, and the 13 GPU tests skip cleanly without CuPy (CuPy sits behind `find_spec`, same pattern as `test_predictive_gpu.py`). Probes on the NumPy path — 0-D `-0.0`, empty, complex/float16/bool, structured, read-only, NaN payload, strided/transposed — all keep identical bytes and don't alias the host array. A fake namespace with #276's 0-D sign loss is handled. ruff, module-size and contract checks pass. I did not run anything on a GPU.

## Verdict

Approve. I'd keep it out of `count_scaled._array`: that path receives device-resident arrays on every operation inside `predictive_cupy`, so wiring it in would need a type branch and a read-back on a hot path, and it would change the core #276 treats as correct.
