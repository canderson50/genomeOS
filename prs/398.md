## Body

closes #192

`OBSERVATIONS_SCHEMA` and `CARRIER_OBSERVATIONS_SCHEMA` set `coerce=True` while declaring the counts and date bounds as `pa.Column(int)`. Pandera coerces before it checks and numpy int casting truncates, so on the pre-fix tree:

    an          200.5 -> ACCEPTED as 200
    ac          50.7  -> ACCEPTED as 50
    date_lower  3.9   -> ACCEPTED as 3

That is the silent coercion §12 forbids, in the schema written to enforce it.

Worse, and not in the issue title: the cross-field checks run on the *coerced* values, so

    ac=200.9, an=200 -> ACCEPTED as ac=200

A row whose allele count exceeds its allele number passed `ac_le_an` because truncation cut it down to 200 first. Truncation did not merely lose precision, it manufactured conformance to the invariant, and `carriers_le_individuals` and `date_lower_le_upper` had the same exposure.

The eight count and date columns become pandas' nullable `Int64`. Its casting is safe rather than truncating: it raises on a non-integral value while still accepting an integral float like 200.0, which every adapter computing `2 * n` in floating point produces. `coerce=True` stays, so nothing else in either schema moves — column-level `coerce=False` cannot help here, since schema-level coercion wins, exactly as the existing note above the boolean column records.

This is the general form of the defect fixed adapter-locally in #154/#160, where AFND's `int(n)` truncated a fractional sample size. That fix protected one adapter; every other source still reached a coercing schema.

The dtype is confined to the validation boundary. `observations/ingest.py` reads the store back through DuckDB, which sees BIGINT either way, so a rebuilt store still loads as plain int64 and the consumers in `surfaces/fit.py`, `surfaces/mask.py` and `validation/crossval.py` — all of which already call `.to_numpy(dtype=...)` — are untouched.

Design sections: §6, §12. Schema change, so `contract/` is regenerated: eight `dtype` entries move int64 -> Int64.
