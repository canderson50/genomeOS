## Body

Small and standalone, so it can land ahead of #124 — it is what lets anyone reproduce a behaviour claim, including the one under discussion in #120.

## Why

#120 and `main` disagree about whether `nuts={"chain_method": ...}` reaches the sampler. **Both readings can be correct**, because nothing pinned the version a claim was made against: `pymc>=5.16` resolves to **6.3.1** here, and PyMC changed how NUTS options are passed between 5.x and 6.x. That is enough for two contributors following the documented install to disagree about what the code does while each being right about their own machine.

## What

**Upper bounds** on the libraries whose behaviour the model depends on: `pymc<7`, `arviz<2`, `numpyro<1`, `pandas<4`, `h3<5`. Deliberate rather than defensive — a major version of any of these changes semantics we rely on, and `pymc` has already done so.

**`requirements.lock`** — all 230 packages, compiled `--universal` so one file installs on macOS, Linux CI and a pod:

```bash
uv venv --python 3.12 && source .venv/bin/activate
uv pip install -r requirements.lock
python -m pip install -e '.' --no-deps
```

**`scripts/env_report.py`** — prints installed versions, then **spies on `sample_jax_nuts`** to report where each channel's options actually land:

```
nuts={"chain_method": "vectorized"}                -> 'vectorized', no warning
nuts_sampler_kwargs={"chain_method": "vectorized"} -> 'vectorized', DEPRECATED
```

Shipping the probe rather than the conclusion is the point. A test that mocks `pm.sample` can only confirm what our own code *passes* — it can never tell you what PyMC does with it, and it will keep passing after PyMC changes underneath. The probe stubs one level deeper, at the boundary where behaviour is actually decided.

## A finding this surfaced, left deliberately unfixed

Checking installed versions against declared bounds found the local venv on **`fastapi 0.141.1`** while `pyproject.toml` declares `>=0.115,<0.120` and the lock pins `0.119.1`.

The declared bound is the project's intent and CI honours it, so **the venv is what drifted** — every local test run on that machine has used a different FastAPI than CI. I have *not* widened the bound to make the violation go away: that would be editing the spec to match an accident. The fix is to reinstall from the lock, which is what this PR enables. Flagging it because it means local green and CI green have not been testing quite the same thing.

## Verified

- `pytest` — **346 passed**
- `ruff check .` clean; module-size, private-file, contract, smoke all pass
- `scripts/env_report.py` runs and produces the table above
- Every installed package except the noted `fastapi` satisfies the declared bounds

## Not done

CI still installs from `pyproject.toml` rather than the lock. Switching it would make reproducibility enforced rather than available, but it also means a new dependency requires regenerating the lock, and it stops CI noticing upstream breakage early. Worth deciding deliberately rather than as a side effect of this PR.
