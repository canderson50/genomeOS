Your draft reason, the full browser suite, is resolved: CI e2e passed 4/4. But no Playwright spec visits `/app/compare/`, so that pass doesn't cover the new page.

## Must fix: the compare page still uses the pre-#437 data base

`compare.astro:13-18` sets `artifactDataBase = siteDataBase`. Since #437, `app.astro` reads `PUBLIC_ATLAS_DATA_BASE_URL` (the GCS bucket), and `dist/` no longer contains grids or surfaces. I built the merged tree with a bucket base: `/app/` bakes in the bucket; `/app/compare/` bakes in `"/data/atlas/"`. In a browser against a cross-origin data server:

```
Atlas request failed with HTTP 404: grids/h3-r4.ccbf19c4a606d017.gosa
404 http://127.0.0.1:4352/data/atlas/surfaces/hbs-rs334/v3/map-2026-08/render…gosa
```

It fails closed, which is good, but the deploy gate only checks `dist/app/index.html`. **Suggested:** one shared helper for both pages' bases (including `#atlas-data-bases` and `assertE2eHooks`), extend `check_atlas_web_data.py --production` to the compare page, and add one Playwright spec for `/app/compare/`.

## Must fix: four failing tests after merging `main`

- `atlas-data-base-config.test.ts:114`: the compare page names the env var. Same root cause as above.
- `atlas-module-size.test.ts:20,24`: `AtlasExplorer.tsx` is 768/799 lines against caps of 755/784, because `main` grew it too. Passing the props object straight into `useComparisonExplorer` should get it back under.
- `site-wide.test.ts:135` (ruling 44, from #462): `AtlasComparison` now holds react-dom. Add it to the allowlist; it is part of the Atlas app.

## Should fix

- **The checksum reads as the source's checksum.** `ingest.py` hashes local bytes, but the contract shows them as `sha256` beside the Pan-UKB `asset_uri`, and the policy accepts any allowlisted host plus any hash. Your description says this doesn't certify the URI; the contract should say so too. `ingested_bytes_sha256`, or a `checksum_basis` field, would do it, and is cheap before anything consumes it.
- **The older routes bypass the new policy.** `/v1/panukb/.../associations` (`api.py:104,140`) serve the same rows with no refusals. Either route them through `provenance_issues` or note the divergence.
- **`/evidence` runs a full aggregate on every load.** It calls `audit`, a GROUP BY plus three anti-joins over all associations, unauthenticated on the Cloud Run app. Fine at zero rows; worth caching or keeping in the CLI.

## For the expert review on #282

Both panels share one palette over different ranges (0.08–17.3% vs 1.4–21.8% for the HbS/G6PD pair), so the same colour means different values, and that pair in particular invites a co-selection reading. The GRCh37 identifiers are fine as an explicit, assembly-prefixed contract, but any future map join needs liftover and an allele-orientation check.
