**Correction — what this commit actually does, in two steps:**

**1. A fractional sample size is refused, not truncated.** `refuse(freq["n_indiv"].notna() & (freq["n_indiv"] % 1 != 0), "fractional_sample_size")` runs on the raw parsed float, before any integer cast, and before the duplicate check so the row is reported for its actual defect. ### bschilder, 2026-09-10T16:05:56Z (https://github.com/genomeOS/genomeOS/pull/160#issuecomment-5621701345)

Answering the open question from this PR's "What a reviewer should check", since it was left unsettled at merge.

**Hashing the parsed float was the right call, and the raw 4-dp string would have been the worst of the three options.** Parsing is what makes `"0.2500"` and `"0.25"` hash alike; the raw string produces different ids for them (verified: `71f74ff2…` vs `9f6b813f…`), so a cosmetic AFND release would re-mint records.

**But the float-repr concern was real, just not where it was aimed.** `stable_source_record_id` hashes `str()` of each part, and `str()`/`repr()` diverge for NumPy scalars under NEP 51. The frequency is safe, because iterating a NumPy-backed float column unboxes to a native `float`. The sample size is not: `n_individuals` is a nullable `Int64`, an extension array, whose values iterate as `np.int64` rather than unboxing. So after this PR a NumPy scalar does reach the hash, in both AFND adapters. Confirmed by spying on the real call:

```
frequencies identity part types: (str, str, str, str, float, int64)
carriers    identity part types: (str, str, float, int64)
```

No id is wrong today, since `str(np.int64(200))` is `"200"`. The exposure was that every published AFND id would re-mint if a future NumPy changed `int64.__str__`, with no test to catch it.

Fixed in #229, which converts at both call sites and adds a spy test per adapter plus an invariant test, with both pinned digests unchanged as proof nothing moved.

The tempting third option, hashing `f"{af:.4f}"`, is deferred to #228 as a decision rather than a commit: `str(0.125)` is `"0.125"` and `f"{0.125:.4f}"` is `"0.1250"`, so it re-mints every identity and needs a `data_version` bump. It also has a scientific wrinkle worth settling first, since it would silently merge measurements if AFND ever publishes more than 4 dp.
