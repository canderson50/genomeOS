## Body

## What this changes, and why

AGENTS.md's "Current, and what CI must keep passing" block listed only the Python gates. The `pages` workflow's `validate` job also gates PRs, so a contributor who ran the documented list and saw green could still get a red build. That is what happened on #295.

This adds that job's steps to the block, run from `website/` on Node 24 (`package.json` `engines`):

- `npm run format:check`
- `npm run check`
- `npm test`
- the custom-domain build and its link check
- the fallback build and its link check
- `npm run test:e2e`

The issue named the first three. I listed every step the job runs, because documenting a subset would leave the same gap for the build, link and browser checks.

**Three things turned up while checking the issue against the repo:**

1. **`CONTRIBUTING.md` keeps its own copy of the gate list** rather than pointing at AGENTS.md. It says "CI runs the same set", so the issue's "one edit covers both routes" didn't hold. I added a short pointer there to the website gates, rather than a second copy of them.
2. **That same list was missing `python scripts/check_commercial_use.py`,** which CI runs and AGENTS.md already lists. It's the same "documented list ≠ CI" defect in the same block, so I added the line. If you'd rather it be separate, it's one line to drop.
3. **`pages.yml` runs only on PRs touching `website/**`.** `scripts/export_atlas_web.py` is the Python half of the payload contract in `website/src/atlas/contracts.ts`. So an exporter-only PR never triggers the website gates, and CI can be fully green with the TypeScript half broken. The new paragraph under the block says so, and tells contributors to run the website gates for exporter changes too.
   - I did not change the workflow. Widening its path filter to include the exporter is a CI decision, and I'd rather it get its own issue.
