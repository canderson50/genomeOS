## Body

## TL;DR

A saved PubMed search once claimed it found 25 papers even though its raw response contained 58. This PR makes GitHub compare every saved search manifest with the response that produced it, so cut-short searches, substituted papers, and malformed search records are reported immediately. For contributions from forks, GitHub runs our trusted checker over the contributor's TSV/JSON files; contributors cannot replace the checker that judges their data.

---

## Problem and resulting behavior

The `lct-enattah-2007` slice merged with a Q3 manifest containing 25 candidates while the committed PubMed response contains 58. The file looked complete, and the discrepancy was only found by replaying the search later.

This adds a generic, offline reconciliation check. For every corpus whose `PROVENANCE.json` declares discovery payloads, it now requires:

- each PubMed payload to parse, contain unique numeric PMIDs, and satisfy `count == len(idlist)`;
- manifest rows selected by the exact `(search_id, manifest_version)` pair to reproduce the payload's identifier set and count;
- declared payloads and declared manifest versions to exist; and
- malformed provenance to name the corpus, query, and missing field without a traceback.

The check distinguishes two different defects. A shorter manifest gets pagination-specific remediation. A same-size manifest containing the wrong PMID is reported as an undeclared-source provenance gap, including bounded examples of the unexpected and missing identifiers. The check derives each search identifier again with `make_search_id`; a manifest cannot pass by agreeing with an identifier copied from itself.

## Fork-safe CI boundary

Issue #248 requires trusted checker code over contributor-authored data. The first version of this PR added the check to the ordinary PR job, which executes the PR checkout and therefore did not satisfy that boundary.

The final implementation uses a dedicated `pull_request_target` workflow:

- the base SHA is checked out as `trusted`;
- the contributor SHA is checked out separately as `candidate`;
- permissions are repository-read-only;
- credentials are not persisted in either checkout;
- only the trusted project is installed;
- only `trusted/scripts/check_manifest_payload_counts.py` is executed; and
- the candidate checkout is supplied only as the fixtures root.

The workflow also runs on pushes to `main`. Because `pull_request_target` loads workflows from the base branch, this new workflow cannot run on the PR that introduces it; the push after merge validates the bootstrap, and subsequent literature-data PRs use the trusted base revision. Updating the checker and introducing data that needs the update therefore requires two PRs, preserving the trust boundary.

## Historical defect and adversarial cases

The test suite mutates temporary copies; committed fixtures are never edited.

- Manifest truncated to 25 of 58 → refused with pagination remediation.
- Manifest containing 58 rows but one substituted PMID → refused as a provenance gap.
- Payload count 57 with 58 returned identifiers → refused.
- Declared version absent from every manifest → refused.
- Duplicate or non-numeric PMIDs → refused.
- Missing `executed_at` → contextual refusal naming the corpus/query/field, with no traceback.
- Screening rows with the same `search_id` but a later manifest version → correctly excluded from discovery reconciliation.
- Non-manifest TSVs → ignored based on their headers.

The duplicate scan uses `Counter`, so a 100,000-result payload is processed in linear time.

## Scope

This advances #248 and #272 without closing either. It changes no manifest, payload, screening decision, evidence row, model, or serving behavior. The older published LCT manifest remains recorded as the historical truncated capture; the corrected pending snapshot is the one whose payload provenance is declared and checked.

## Finding 1 — the message cannot describe the failure it just caught

Counts and sets are both compared, but only counts reach the error. Swap a single `candidate_id` for
a PMID the search never returned, leaving the row count identical, and the check correctly refuses
with:

```
- lct-enattah-2007/Q2: manifest records 1 candidate(s) under lct-rs4988235@2026-09-12.1
  for a payload matching 1
```

One and one, offered as the defect. Then the guidance underneath says:

> A manifest recording fewer candidates than the payload matched is a truncated or paginated
> capture, not a screened one...  Re-fetch with scripts/fetch_pubmed_manifest.py

That is the wrong diagnosis. Nothing was truncated. The manifest names a paper that did not come
from the search, which is arguably a worse defect than truncation — a candidate from an unrecorded
source is exactly the provenance gap this corpus machinery exists to close — and the contributor is
sent to fix pagination.

The information already exists. `same_set` is computed, and the diagnostic line above the failure
even prints `set match False`. It just never reaches the message.

**Suggested:** branch the message on which comparison failed. Something like "records N candidates
under V, but K of them are not in the payload it declares" for the set case, keeping the current
wording for a genuine count mismatch, and making the remediation text conditional too.

**Why it went unnoticed:** ten tests, none touching the set-mismatch path. Worth one test, since the
mutation takes a single character to produce.

## Finding 2 — malformed provenance exits with a traceback

`query["query"]` and `query["executed_at"]` are read with brackets while `name` and `payload` on the
same object use `.get()`. Remove `executed_at` from one query and the run ends in:

```
  File "scripts/check_manifest_payload_counts.py", line 117, in inspect
    search_id = make_search_id("pubmed", query["query"], query["executed_at"])
KeyError: 'executed_at'
```

Exit code is 1, so CI does fail — but a contributor gets a stack trace rather than a line naming the
corpus, the query and the missing field. For a gate people will actually hit, that is the difference
between a fixable message and a bug report. The same guard the payload reader already uses would
cover it.

## What I checked first: does this re-erect the barrier from #291?

No, and the scoping is the reason. `inspect` returns no problems when a corpus has no discovery
block, so a paper that arrived because somebody knew about it is not penalised for lacking a search
it never ran. I built that case — a corpus whose provenance says "named by a collaborator; no search
was run" — and it exits 0.

That is the right shape. The check tests a claim a manifest makes about itself. It does not require
that the claim be made.

## What is good, verified rather than assumed

- **Identifying a manifest by its header, not its filename.** A corpus directory also holds the
  evidence ledgers, and a filename rule would read those as manifests with zero candidates and
  report them truncated. Tested.
- **Pairing rows on `(search_id, manifest_version)` rather than the identifier alone.** Screening
  republishes a discovery snapshot under a new version keeping the same identifier, and the hbb
  corpus carries the same three identifiers in both files. Matching on the identifier alone would
  compare a payload against the union of two manifests and refuse a correct corpus. A real trap, and
  tested.
- **Re-deriving identifiers through `make_search_id` instead of reading them.** This is the detail
  that gives the check teeth: a manifest cannot pass by agreeing with itself.
- **The scoping is honest about what it does not cover.** The published truncated manifest is not
  examined, because nothing declares a payload behind it, and the description says so rather than
  implying the corpus is now clean.

## One consistency note, not a finding

`main()` reads process arguments directly, so the tests monkeypatch `sys.argv`. That works. Both
gates touched yesterday (#304) now take an explicit argument list instead, which makes them callable
from a test without patching global state. Worth matching while this file is open.

Approve once Finding 1 has a fix and a test. Finding 2 is a small hardening on the same function and
is worth doing in the same pass.

## 2 — `base.sha` does not track the base branch

The trusted checkout uses `github.event.pull_request.base.sha` (`manifest-payload-gate.yml:28`).
This PR's own `base.sha` is still bc42062, after two later pushes and with main 66 commits ahead. A

description ("fix the checker, then the data") does not hold. No open PR touches these paths, so
nothing breaks on merge. `github.sha`, which under `pull_request_target` is the base-branch tip, is
the one-line fix.

## 3 — The payload path can leave the candidate tree

ESearch-shaped JSON leaks, and the job has no secrets and no saved token. Still, `resolve()` plus
`is_relative_to(corpus)` plus a symlink refusal makes the docstring's "reads committed data"
literally true.
