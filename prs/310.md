## Body

## TL;DR

A saved PubMed search once claimed it found 25 papers even though its raw response contained 58. This PR makes GitHub compare every saved search manifest with the response that produced it, so cut-short searches, substituted papers, and malformed search records are reported immediately. For contributions from forks, GitHub runs our trusted checker over the contributor's TSV/JSON files; contributors cannot replace the checker that judges their data.

---

## Problem and resulting behavior

The `lct-enattah-2007` slice merged with a Q3 manifest containing 25 candidates while the committed PubMed response contains 58. The file looked complete, and the discrepancy was only found by replaying the search later.

This adds a generic, offline reconciliation check. For every corpus whose `PROVENANCE.json` declares discovery payloads, it now requires:

- each PubMed payload to parse, contain unique numeric PMIDs, and satisfy `count == len(idlist)`;
- manifest rows selected by the exact `(search_id, manifest_version)` pair to reproduce the payload's identifier set and count;
- declared payloads and declared manifest versions to exist; and
- malformed provenance to name the corpus, query, and missing field without a traceback.

The check distinguishes two different defects. A shorter manifest gets pagination-specific remediation. A same-size manifest containing the wrong PMID is reported as an undeclared-source provenance gap, including bounded examples of the unexpected and missing identifiers. The check derives each search identifier again with `make_search_id`; a manifest cannot pass by agreeing with an identifier copied from itself.

## Fork-safe CI boundary

Issue #248 requires trusted checker code over contributor-authored data. The first version of this PR added the check to the ordinary PR job, which executes the PR checkout and therefore did not satisfy that boundary.

The final implementation uses a dedicated `pull_request_target` workflow:

- the base SHA is checked out as `trusted`;
- the contributor SHA is checked out separately as `candidate`;
- permissions are repository-read-only;
- credentials are not persisted in either checkout;
- only the trusted project is installed;
- only `trusted/scripts/check_manifest_payload_counts.py` is executed; and
- the candidate checkout is supplied only as the fixtures root.

The workflow also runs on pushes to `main`. Because `pull_request_target` loads workflows from the base branch, this new workflow cannot run on the PR that introduces it; the push after merge validates the bootstrap, and subsequent literature-data PRs use the trusted base revision. Updating the checker and introducing data that needs the update therefore requires two PRs, preserving the trust boundary.

## Historical defect and adversarial cases

The test suite mutates temporary copies; committed fixtures are never edited.

- Manifest truncated to 25 of 58 → refused with pagination remediation.
- Manifest containing 58 rows but one substituted PMID → refused as a provenance gap.
- Payload count 57 with 58 returned identifiers → refused.
- Declared version absent from every manifest → refused.
- Duplicate or non-numeric PMIDs → refused.
- Missing `executed_at` → contextual refusal naming the corpus/query/field, with no traceback.
- Screening rows with the same `search_id` but a later manifest version → correctly excluded from discovery reconciliation.
- Non-manifest TSVs → ignored based on their headers.

The duplicate scan uses `Counter`, so a 100,000-result payload is processed in linear time.

## Scope

This advances #248 and #272 without closing either. It changes no manifest, payload, screening decision, evidence row, model, or serving behavior. The older published LCT manifest remains recorded as the historical truncated capture; the corrected pending snapshot is the one whose payload provenance is declared and checked.
