## Body

**Summary**

Advances #111 (4 of 10 cross-validation folds fail to converge). It does not close it: the folds may still fail, and the root cause is untouched.

The issue lists four remedies, cheapest first; this is the cheapest one only. `target_accept` was not settable at all — FitConfig had no such field, so every fit ran at PyMC's implicit 0.8 and the issue's second suggestion was unreachable from the CLI. It now defaults to 0.8, so the surfaces already published are unaffected, and validate_holdout.py raises it to 0.9 for folds alongside a draw count of 1000, up from the 400 that produced ESS 61-143 against a floor of 200.

**Changes**

- `FitConfig.target_accept`, default `0.8`. The default is PyMC's own, so the surfaces already published are unaffected; raising it is opt-in at the call site that needs it. Validated to be strictly within `(0, 1)`.

- `scripts/validate_holdout.py` raises it to `0.9` for folds and lifts draws 600 → 1000. The failing run used 400, which produced ESS 61–143 against a floor of 200.

- `chain_method` routing fix — see below.

- `min_ess` is deliberately not touched. Lowering a convergence gate so more folds pass would weaken a scientific gate to make a run go green; if this budget is not enough the next step is diagnosis, not a lower bar.

**The `chain_method` fix**

Found while plumbing this through, and fixed here because it is the same block and it decides whether the larger budget is affordable: chain_method="vectorized" has never reached numpyro. On the external-sampler path pm.sample pops its `nuts` dict, keeps only target_accept from it, and discards the rest without warning, so the option was silently inert and every chain was drawn sequentially on a single GPU. It now travels in nuts_sampler_kwargs, which pm.sample forwards verbatim. This changes RNG streams, so fits are statistically equivalent but not bit-identical to previous runs.

**Recorded, not acted on**: cohort_id is the contributing study, not the survey site (332 surveys, 151 studies, only 41 contributing more than one site). For a singleton study, cohort_sd*cohort_z and the beta-binomial concentration describe the same single residual — a weak-identifiability ridge. A random split cuts multi-site studies apart and converts identified cohorts into singletons in training, where k-means spatial folds keep a study's clustered sites together, which would explain the observed 3/5 random vs 1/5 spatial failure split. It would also mean predict_observation's premise, that a held-out survey belongs to a cohort the model never saw, is violated whenever a study straddles the split. Untested; needs its own issue.

**Design sections**

§7 (surface fit), §7.1a (ascertainment offsets), §8 (held-out validation). No schema changed, so `contract/` is untouched.

**Not verified, and it matters**: whether this actually gets 10/10 folds through the gate. That needs the real MAP HbS corpus (`scripts/fetch_map_hbs.py`) and a GPU run of `scripts/validate_holdout.py` — the reported failures came from an A100. This PR makes the knobs available and the budget affordable; it does not demonstrate the outcome.
No figure is included because nothing renderable changed — no surface, mask, or burden layer is affected, only sampler configuration.

**What an expert should check**:

Whether raising `target_accept` and draws is the right first move at all, given the identifiability argument above. If that mechanism is real, this buys efficiency without fixing the underlying ridge, and #111's biased-surviving-folds concern stays open regardless of how many folds now pass.

## What I'd take unchanged

- `target_accept` as a `FitConfig` field, defaulting to PyMC's own 0.8 so already-published surfaces are untouched. The reasoning in the docstring is exactly right: a fold trains on `(k-1)/k` of the data and has to buy with sampling budget what it lacks in data.
- Range validation on `(0, 1)`, and the parametrised test for it.
- `draws=1000` + `target_accept=0.9` for the folds. Four of ten folds missed the ESS floor at 61–143 (#111), and this is the cheapest thing that could fix it.

Making it opt-in at the call site rather than raising the global default is the right call, and worth saying explicitly.

## Where I get a different answer, and why I think we're both right

The PR states that `nuts={"chain_method": "vectorized"}` was *"silently inert"* and that `pm.sample` *"pops that dict and keeps only `target_accept`, dropping everything else without a warning."*

On **pymc 6.3.1** I measure the opposite. `_sample_external_nuts` explicitly lifts a set of options out of the `nuts` dict into top-level arguments for `sample_jax_nuts`, and `chain_method` is in that list:

```python
jax_top_level_params = (
    "target_accept", "jitter", "keep_untransformed",
    "chain_method",              # <-- lifted, not dropped
    "postprocessing_backend", "postprocessing_vectorize", "postprocessing_chunks",
)
```

Spying on `sample_jax_nuts` to see what actually arrives:

| channel | `chain_method` arrives | deprecation |
|---|---|---|
| `nuts={...}` | `'vectorized'` | none |
| `nuts_sampler_kwargs={...}` | `'vectorized'` | **yes** |

PyMC 6's docstring for the latter reads: *"Deprecated. Pass NUTS keyword arguments via `nuts={...}` instead"*, and internally it converts it straight back into `nuts`.

**But `pyproject.toml` pins `pymc>=5.16`, and that resolves to 6.3.1 here.** The `nuts=` API and this deprecation both look like PyMC 6 changes, so if you're on 5.x your reading may be correct for your environment and mine for mine. Nothing in the repo said which version a claim was made against, which is a repo problem rather than a PR problem — so I've fixed that rather than just disagreeing.

## Tooling to settle it (on `feat/afnd-live-harvest`, PR #124)

```bash
python scripts/env_report.py
```

Prints your installed versions, then **spies on `sample_jax_nuts`** and reports where each channel's options actually land in *your* environment. And to match this environment exactly:

```bash
uv venv --python 3.12 && source .venv/bin/activate
uv pip install -r requirements.lock          # all 222 packages pinned
python -m pip install -e '.' --no-deps
```

If your output differs from the table above, that is a real finding about version support and I'd want it in the code as a version check rather than a silent choice of channel. If it matches, then on 6.x the change swaps a current API for a deprecated one and adds a `FutureWarning` to every fit.

## One point that holds either way

`test_sampler_options_travel_by_the_channel_pymc_actually_forwards` mocks `pymc.sample` entirely, so it can only confirm what `fit_surface` *passes* — it never exercises PyMC's forwarding, despite the name. It will keep passing after PyMC changes underneath, which is the case it most needs to catch. The probe above stubs one level deeper, at `sample_jax_nuts`, because that is where the behaviour is actually decided.

## Suggested split

1. Merge `target_accept` + the fold budget now — no objection, genuinely useful.
2. Hold the `chain_method` change until `env_report.py` output is compared, and rename or re-scope that test so its name matches what it verifies.
3. Separately, we should pin an upper bound (`pymc<7`) or adopt the lockfile in CI, so this cannot recur.

Thanks for chasing #111 — the fold-budget diagnosis is right, and the four failing folds at ESS 61–143 were the clearest lead in it.
