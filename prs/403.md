## Step 2 — the layer the parity run consumes, and the live layer

The input Step 1 could not reach is fetched by this repository's own tool rather than reconstructed:
`scripts/fetch_map_hbs.py --out <path>` writes the `Explorer:HbS_Data` WFS response
(`outputFormat=csv`, no credentials).

- Fetch windows 2026-10-07T22:08:31Z-22:08:33Z and 22:14:06Z-22:14:07Z. Both responses carried 1,287
  data rows. The byte count is not stable (below), so it is not used as a property of the layer.
- **The response is not byte-stable, and the reason is one column.** GeoServer's `FID` is a
  per-request feature id (`...-6220`, `...-6728`, `...-6764` across three requests). With `FID`
  removed every request is identical. The data-column digest is SHA-256 over the response
  re-serialized as CSV with the `FID` column dropped, the header row kept, `csv.writer`
  `QUOTE_MINIMAL` on a comma delimiter, LF line endings, no trailing newline, UTF-8:
  `b3174937aa32ea01c0670b564359394779d7d860f7d5f24bf56495b9bf0d3ca5`, over 1,287 rows and 350,304
  characters, identical on two independent fetches on 2026-10-17. The 2026-10-07 value
  `3d6a4f60...` is retired: it hashed a naive comma join, and 1,277 of the data fields contain a
  comma, all of them in `citation`. Whole-response SHA-256 varies per request and identifies
  nothing. A later check compares the data-column digest and the row count, and reads neither a
  changed `FID`, a changed byte count nor a changed response digest as a changed layer.
- Second layer: the committed artifact the P1 path holds,
  `website/public/data/atlas/hbs-rs334.observations.json` (`map-2026-08`), 1,071 records, every id
  present in the live layer. The live layer has grown by 216 ids (1,071 to 1,287), so the comparison
  runs twice: against the immutable artifact, and against the live layer.

**Result: no collision in either layer.**

- Study identity: 0 occurrences of the identifiers in the committed artifact (1,071 records) and in
  the live layer (1,287 rows), searched over every field.
- All 41 Sudan rows in the live layer are also in the committed artifact and none is this study; they
  resolve to ten other studies — Foy 1964 (13), Vella 1966 (7), Omer 1972 (7), Lauder & Ibrahim 1970
  (3), Roberts & Lehmann 1955 (3), Saha & Patgunarajah 1981 (3), Vella 1965, Saha 1981, Samuel 1981,
  Bayoumi 1985, Nasr 2008.
- Count identity, in the layer's own units. The counts are derived, and the derivation is pinned to
  the committed artifact rather than chosen: **an = 2 x (AA + AS + SS)** with a blank `hbaa`
  recovered as `sample_size - hbas - hbss`, and **ac = hbas + 2 x hbss** with a blank `hbss` read as
  zero. That reproduces the payload's `an` and `ac` exactly on **1,071 of 1,071** records, 0
  mismatches. Deriving `an` as `2 x sample_size` is wrong for 207 of them, which is the error an
  earlier draft of this section made and which the re-check caught.
- Under that rule the comparison covers **1,185 of 1,287 live rows** (102 are not derivable). No row
  carries either pair, 448/121 or 492/98. Nearest rows, named so the refusal is checkable: at an 492,
  id 1193 Schiliro 1986 (Italy) has ac 5 and id 879 (Burkina Faso) ac 19; ac 98 belongs to id 406
  (Kenya, an 916), id 994 (Gambia, an 994) and id 1034 (India, an 1018); ac 121 belongs to id 1075
  (Belgium, an 19,150). No row has a `sample_size` of 224 at all.
- **Homonym control:** the single population-label hit is survey id 12, Adamson 1951, *Nigeria*,
  "Haematological and biochemical findings in Hausa males", present in both layers. Hausa is an
  ethnicity across Nigeria, Niger and Sudan, so a label-only match would have reported a Nigerian
  1951 survey as a duplicate of this row. The match is refused.

All three are fixed in 3222259.

**1. The digest.** You were right that it could not be recomputed, and the reason is worse than an unstated serialization. The original was a naive join: each row's fields joined with a comma, rows joined with a newline, header first, no trailing newline. No CSV writer produces that, which is why all twenty of your attempts missed. It is also a poor fingerprint: 1,277 of the data fields contain a comma and every one of them is in `citation`, so the join cannot tell some changes apart.

So the digest is now canonical and the serialization is stated in the doc: FID dropped, header kept, `csv.writer` with `QUOTE_MINIMAL` on a comma delimiter, LF line endings, no trailing newline, UTF-8. The value is `b3174937aa32ea01c0670b564359394779d7d860f7d5f24bf56495b9bf0d3ca5`, over 1,287 rows and 350,304 characters. It came out identical on two independent fetches today, and parsing the serialization back reproduces the table exactly, so it is a faithful fingerprint rather than a value that happens to match. The old value stays in the doc, marked retired, with the reason, so the change is auditable rather than silent.

**2. The byte count** is out of the proposed check. It is now an observation with the mechanism spelled out: the per-request `FID` changes length, and one character on each of 1,287 rows is 1,287 bytes. It read 402,028 on the 7 October requests and again on two today, with identical data columns. The check is the data-column digest plus the row count, and the doc says that neither `FID`, nor the byte count, nor the whole-response digest identifies the layer.

**3. The 342** is gone from the header, and the `highest entry seen, 341` observation is gone with it, so there are no longer two numbers to disagree. No entry count is quoted anywhere now, for the reason line 130 already gives.

On your preference for the script: the serialization above is enough to recompute with any CSV reader, and I kept the PR docs-only so it can land. If you would rather have the tool, I will add a small `scripts/map_hbs_layer_digest.py` in a follow-up that fetches the layer and prints the digest and the row count, and then the doc can point at the tool instead of restating the recipe.
