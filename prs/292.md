## Body

## TL;DR

Two people installing this project could end up with different versions of a numerical library, and
one of those versions crashed the model-fitting code. This pins it so everyone gets a version that
works.

**Read the correction at the bottom before trusting the reasoning.** A review after this was written
found that the crash had already been fixed upstream by a different library, and would have reached
us anyway. The pin is still worth keeping as cheap insurance, but it is not what fixed the bug.

---

## Problem and result

An editable scientific-extras install could admit NumPy 2.5.x even though issue #285 records the PyTensor/Numba fitting path reaching the removed `np.row_stack` alias under NumPy 2.5.2. The lock happened to retain NumPy 2.4.6, so lock-based and extras-based contributors could get different runtime behavior.

The `surfaces` extra now declares `numpy<2.5`, and a semantic dependency-contract regression verifies that 2.4.6 is admitted while the recorded 2.5.2 boundary is refused. `requirements.lock` was regenerated with the required universal `--upgrade` command; it retains NumPy 2.4.6 and advances compatible patch releases including PyMC 6.3.2, PyTensor 3.3.2 and Numba 0.67.0.

Today's pre-change unbounded resolution selected NumPy 2.5.3 / PyTensor 3.3.2 and did not reproduce the older failure in focused fitting tests. This PR therefore addresses the recorded failing compatibility boundary and does not claim that every current NumPy 2.5.x combination is broken.

This supports Atlas design §7 offline surface inference. It changes no scientific model, schema, serving behavior or publication gate.

Closes #285

## Correction added at review (2026-09-15)

An independent review re-ran the resolution and inspected the upstream source. Two of the claims
above need adjusting, so the record is accurate:

> ~~The `surfaces` extra now declares `numpy<2.5` [...] This PR therefore addresses the recorded
> failing compatibility boundary.~~

**Numba 0.67.0 already fixed this crash, independently of the NumPy version.** Diffing numba's
released source distributions:

- `0.66.0` — `if numpy_version >= (2, 0): overload(np.row_stack)(impl_np_vstack)`, unconditional,
  so it reaches the removed alias.
- `0.67.0` — `if numpy_version >= (2, 0) and numpy_version < (2, 5):` with the comment *"Numpy 2.5
  removed np.row_stack, so only test it if it's present."*

Both the capped and uncapped resolutions select `numba==0.67.0`, so the fix arrives from the routine
`--upgrade` lock regeneration whether or not the `numpy<2.5` line exists. That is also why this PR's
own validation could not reproduce the failure — not a fluke, and not a NumPy-side change.

**The pin is still worth keeping**, as cheap defence in depth consistent with this repository's
existing practice of putting upper bounds on libraries that have already caused two contributors to
disagree. It is a belt-and-braces guard rather than the active fix.

### What the review verified

- `numba` reaches the tree only via `pytensor`, and `pytensor` only via `pymc`, both exclusively in
  the `surfaces` extra. So the bound is correctly scoped: `atlas`, `geo` and `figures` never touch
  that path, and the documented combined install still resolves one shared NumPy for everything.
- The regenerated `requirements.lock` is **byte-identical** to an independent
  `uv pip compile --universal --upgrade` run against this PR's `pyproject.toml`. NumPy stays at
  2.4.6; PyMC 6.3.2, PyTensor 3.3.2 and Numba 0.67.0 land as claimed. No major-version jumps.
- The new contract test is not vacuous: it is red against the pre-PR `pyproject.toml`, green after,
  and fails again if the bound is weakened to `numpy<2.6`.

### Known limitation of the new test

It parses `pyproject.toml` against itself. It does not check `requirements.lock` for drift, so a lock
that disagrees with the declared bound would not be caught here.
