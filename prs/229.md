## Summary

Answers the question left open on #160: whether hashing the parsed frequency rather than the raw
4-dp string makes the identity depend on float repr.

**It does — but not where the question expected, and the fix is not the raw string.**

> Stacked on #227. Review that one first; this PR's own diff is the second commit.

## What the identity actually rests on

`stable_source_record_id` hashes `str()` of each part
([source_ids.py:16](https://github.com/bschilder/genomeOS/blob/17c60f466263113eff3ed58769ff0663fd61046b/genomeos/observations/source_ids.py#L14-L18)).
`str()` and `repr()` diverge for NumPy scalars under NEP 51 — `repr(np.float64(1.5))` is
`"np.float64(1.5)"` while `str()` is `"1.5"` — so the helper's use of `str()` is load-bearing
rather than incidental.

The **frequency** is safe: iterating a NumPy-backed float column unboxes to a native `float`.
The **sample size is not.** `n_individuals` is a nullable `Int64`, an extension array, whose
values iterate as `np.int64` instead of unboxing. So after #160 a NumPy scalar does reach the
hash, in both adapters. Confirmed by spying on the real call rather than reading the code:

```
frequencies identity part types: (str, str, str, str, float, int64)
carriers    identity part types: (str, str, float, int64)
```

That asymmetry between a NumPy-backed column and an extension array is easy to miss, and it is
why the guard is a spy on the real call and not an inspection.

## No id has moved

`str(np.int64(200))` is `"200"`, the same as `str(int(200.0))`. The exposure was never a wrong
id today; it was that **every published AFND id would re-mint if a future NumPy changed
`int64.__str__`, and nothing would catch it.**

Both call sites now convert with `int(n)`, which cannot truncate because a non-integral sample
size is already refused as `fractional_sample_size` (#160 for frequencies, #227 for carriers).

## The alternative I rejected, and why

Hashing an explicit `f"{af:.4f}"` is more self-describing and was the tempting answer. It
re-mints every identity:

```
str(0.125)     = '0.125'   -> afnd-frequencies:7cd70a92...
f"{0.125:.4f}" = '0.1250'  -> afnd-frequencies:6bf5babd...
```

That is a real migration cost against a dormant risk, and it collides with the immutability
invariant (§5): a map someone has cited must not change identity quietly. Keeping `str()` of a
*native* scalar buys the same independence for free. Whether to adopt an explicit canonical
format is filed as a decision in #228, since it needs a `data_version` bump rather than a commit
— and it should probably come with a refusal when the source publishes more precision than the
format preserves, which is a scientific argument the format change on its own would paper over.

Hashing the **raw** 4-dp string, the other option named in #160, is the worst of the three: it
loses the drift protection entirely, since `"0.2500"` and `"0.25"` then produce different ids
(verified: `71f74ff2…` vs `9f6b813f…`).

## What a reviewer should check

Whether pinning the identity to *native Python scalar* types is the right contract, or whether
the better contract is for the adapters to stringify explicitly at the call site so the identity
never depends on any type's `__str__`. I chose the former because it is a one-token change that
preserves every existing id; the latter is cleaner but is the same re-minting decision as #228.
