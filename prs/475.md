## TL;DR

The data the Python pipeline publishes for the website's Atlas now has one explicit version: `"format_version": "1.0"` in `catalog.json`. The website refuses a catalog of a MAJOR version it doesn't know, with a clear error at build time and in the browser. It reads a newer MINOR and ignores the keys it doesn't know. Python only writes the current version and refuses to write anything else.

Nothing in the public bucket changes. The five committed catalogs differ from `main` only in that one key; every object key and digest is unchanged. The rules, and how to bump the version, are in [`docs/web-data-format.md`](https://github.com/genomeOS/genomeOS/blob/feat/web-data-format-version/docs/web-data-format.md).

## What this changes, and why

The Python publication pipeline and the website's Atlas client share a data format. It covers `catalog.json`, the GOSA objects, the exported JSON, the external caches and the GOBD borders. Nothing gave that format as a whole a version, and the strict zod contract meant even a purely additive catalog change had to land in Python and TypeScript together. Since August, 14 of the 34 commits that touched `website/` also changed Python. An explicit, checked version makes compatibility visible, and it's the prerequisite for ever splitting the repo into a science repo and a web repo.

**Where the version lives, and why.** It's in `catalog.json`, replacing the catalog's `schema_version: 1` rather than adding a parallel field.

- The catalog is the single entry point: every other object is named by key and sha256.
- It's committed and deployed with the site (§B.4 ruling), so the client and its catalog always ship together, and changing the version needs no bucket write.
- The binary headers keep their existing u16 slots, which version their own container layout. Each format MAJOR pins the value every slot must hold.
- Putting the format version into GOSA or GOBD headers would change every object's bytes, sha256 and key, so every bump would mean re-encoding and re-uploading the bucket.

**Compatibility rule.**

| Reader | Same MAJOR, same or older MINOR | Newer MINOR | Another MAJOR | Missing or malformed |
|---|---|---|---|---|
| Browser and `/app/` build (`parseAtlasCatalog`) | strict; an unknown key is an error | read; unknown catalog-object keys ignored, known fields still validated, build prints a warning | `AtlasFormatVersionError`; the build fails | refused |
| Python writers (`export_atlas_web.py`, `encode_atlas_web.py` and the fixture builders) | must be exactly current | refused | refused | refused |
| Python enumerators (`web_layout`, used by the publisher and the deploy gate) | read | refused (it may name objects they can't enumerate) | refused | refused |

There is no "missing = 1.0" default anywhere. An unknown key is ignored only if it belongs to a catalog *object*. An unknown support state in `support_counts` is still refused, because a new value in a closed set is a MAJOR change.

**How existing published objects stay valid.**

- Objects carry no format version of their own. An object is valid under a format because a catalog of that format names it by sha256, and its own slots hold the values that MAJOR pins.
- Format 1.0 is exactly what's already published.
- A MINOR bump leaves every key in place.
- A MAJOR bump publishes new content-addressed keys next to the old ones. Nothing is overwritten (§C.2).

**One judgement call to review.** The cross-language tests define "the Python and TS constants agree" as *same MAJOR, and the client's MINOR never ahead of the producer's*, not strict equality.

- With strict equality, every Python MINOR bump would have to touch TypeScript in the same PR, which is the lockstep this work is meant to relax. Under this rule, Python can ship an additive key on its own, and the site builds with a warning until the client adopts the key.
- A MAJOR change still has to land on both sides together.
- The deployed catalog must equal the Python constant exactly.
- Switching to strict equality is a one-line change in each test if you'd prefer it.
