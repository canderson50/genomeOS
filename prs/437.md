## What this changes, and why

This is Part C of the Atlas mobile, fast-load and GCS design. Each Atlas dataset's data now lives in a public Google Cloud Storage bucket, not in the repository. The site keeps only `catalog.json`. The page loads every surface, observation and grid object from the bucket, cross-origin.

**Why.**
- The 90 per-artifact JSON files (30 datasets × surface, observations, manifest) were about 600 MB of tracked data, and each new dataset or re-encode added more.
- GitHub Pages was serving that data on top of the site.
- The bucket serves each object pre-compressed with an immutable one-year `Cache-Control`. Keys are content-addressed, so stale bytes can't stick.
- Load times are unchanged. See "Cold load against the bucket origin" below.

**What changes:**
- **One layout module.** `genomeos/publication/web_layout.py` is pure and 100% covered. It defines object keys, headers, allowed origins and the CORS policy. The encoder, publisher, provisioner and deploy gate all go through it, so they can't disagree. `deploy/atlas-web-cors.json` equals `cors_policy()`.
- **Staging.** `encode_atlas_web.py --with-downloads` writes a staging tree outside the repo. It holds the GOSA objects plus byte-identical copies of each canonical JSON, under `downloads/<id>/<model>/<data>/<id>.<kind>.<sha16>.json`. It also rewrites the catalog's URLs to those keys. Every SHA-256 is unchanged, so existing citations still resolve. `--in` is now required, since the repository has no export left to default to.
- **Provisioning.** `provision_atlas_web_bucket.py` is idempotent. It sets uniform access, `allUsers` object read, the CORS policy and an ownership label. Every call goes through `scripts/atlas_web_gcloud.py`, the repository-wrapped gcloud runner. The unit tests run against a stateful fake gcloud and never touch a real project.
- **Publishing.** `publish_atlas_web.py`:
  - compresses each file once (gzip level 9, mtime 0) and uploads with `--if-generation-match=0`;
  - treats the decoded SHA-256, decoded size and encoding in object metadata as identity, so an identical object is skipped and a different one is a hard error, never an overwrite;
  - verifies every upload by reading it back.
- **Deploy gate.** `check_atlas_web_data.py` checks every catalog object on the bucket: metadata identity, `Cache-Control`, CORS for each production origin, and an end-to-end decode of the critical objects. `--production` also checks the built `dist/`.
- **Site.**
  - `app.astro` is the only reader of `PUBLIC_ATLAS_DATA_BASE_URL`. It validates the value and bakes `#atlas-data-bases`, which the page, the gate, the performance harness and the e2e specs all read.
  - The page also gets a `preconnect` to the data origin.
- **CI (`pages.yml`):**
  - The encode step is gone.
  - On pushes and same-repo PRs, `validate` runs the gate.
  - The build job reads the `ATLAS_DATA_BUCKET` and `ATLAS_DATA_BASE_URL` repository variables. It refuses an empty base or a leftover `ATLAS_CATALOG_PATH` before building, and runs the gate with `--production` before upload.
  - e2e builds against `http://127.0.0.1:4323/`. Playwright starts a second web server there (`website/scripts/serve-atlas-data.mjs`) that serves the fixture tree like the bucket does: with CORS, gzip and the same headers. A new `atlas-cross-origin.spec.ts` pins the cross-origin contract in a real browser.
- **CORS.** The bucket's CORS allows `https://genome-os.org`, `https://www.genome-os.org`, and local dev origins on ports 4321–4323. It does not allow `http://genome-os.org` or the `genomeos.github.io` fallback, because both redirect to `https://genome-os.org` (owner-approved, 2026-10-10).
- **Repository.** `website/public/data/atlas/catalog.json` is replaced by the published catalog. Only the surface, observation and download URLs change, and every SHA-256 is identical. The 90 per-artifact files are removed, and the generated `grids/` and `surfaces/` stay git-ignored. Natural Earth, places and the three external caches stay tracked.
- **Docs.** `docs/data-store.md` and the site's Local development and Deployment pages document:
  - the bucket;
  - the provision → publish → gate → commit-catalog runbook;
  - how to re-encode now that the per-artifact files have left the repository;
  - local development against the bucket or a local staging tree.

### Open finding: the first page load in a freshly launched Chrome is about 3 s slower against the bucket

- **Observed:** desktop run 0's observations-visible was 3,363 ms in I2 and 3,327 ms in I3, against 378–392 ms for runs 1–2.
- **Local control:** against the local cross-origin server, the same run 0 costs only about 130 ms extra (542 ms against 374–413 ms).
- **Phone runs** reuse the already-running browser and show no run-0 penalty.
- **Network probe:** a direct probe of the bucket from a freshly launched Chrome took about 0.2 s end to end: DNS 15 ms, connect about 50 ms, TLS about 30 ms, time to first byte 20–70 ms. Connection setup alone doesn't explain the gap.
- **Status:** I haven't traced the cause. It may be specific to a fresh automated profile, such as Chrome's first-run traffic to Google hosts, or a real first visit may see it too. It doesn't move any median.
- **Next step:** a performance trace of a fresh-profile first load before calling first-visit performance settled. That's filed as #438, so it doesn't block this PR.
