## Body

Small `AGENTS.md` addition covering how issues actually get closed by a merge.

## Two mechanisms, and the reliable one isn't the PR body

**PR body.** GitHub's docs say to [use full syntax for each issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) — `Resolves #10, resolves #123` — so a bare comma list links only the first. Confirmed here: #81's body read `Closes #14, #15, #16, …` and `closingIssuesReferences` returned exactly `[14]`. Re-editing with the keyword repeated returned all eight.

**Commit message.** A squash merge concatenates the branch's commit messages, so a `closes #N` in each commit reaches the merge commit regardless of what the PR body says.

## Correcting my own claim

I originally wrote that the comma list "silently leaves the rest open." **That was wrong**, and worth stating plainly since it was the stated motivation for this PR.

In #81 all eight issues *did* close, at 19:42:32 against commit `3bcf88f`:

```
$ git log -1 --format='%B' 3bcf88f | grep -oiE 'closes #[0-9]+' | sort | uniq -c
   1 closes #14      1 closes #24      1 closes #27
   1 closes #15      1 closes #25      1 closes #28
   1 closes #16      1 closes #26
```

The squash commit inherited all eight per-task commit messages, each carrying its own keyword. The commit messages closed the issues; the PR body didn't, and my later body edit came five minutes after they were already closed.

So the linking rule is real and worth following, but the failure mode I described didn't occur — and it didn't occur *because* of the one-commit-per-issue discipline, which is the habit actually worth writing down.

## What the guidance now says

Do both, and know which is load-bearing: repeat the keyword per issue in the PR body so the linked-issues panel is right, and put `closes #N` in the commit that does the work, because that's the half that survives a squash.
