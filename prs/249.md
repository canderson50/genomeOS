## Body

## What

The slice was merged with no builder and no payloads, so nothing in the repository could reproduce
the 37-row manifest or re-derive the 12 record identifiers. This is that, scoped to the backfill.

- `scripts/build_lct_enattah_fixture.py` — replay by default, every path through `argparse`,
  `--extracted-at` required rather than read from the clock, field rows driven off `TRACKED_FIELDS`
  with a coverage check that fires on drift. Design §§5.2, 5.3.
- `payloads/Q1.json`–`Q3.json` — the raw ESearch response bytes.
- `PROVENANCE.json` — the queries, payloads and timestamps.
- `searches.pending.tsv` — the corrected all-pending discovery snapshot, 70 rows.
- `tests/test_literature_corpus_lct_enattah.py` — the first 7 tests assert the science and are
  unchanged from the merged slice; the rest cover this backfill.
- `docs/audits/lct-enattah-2007-corpus.md` — the truncation finding and its reproduction evidence.

## Scope: the published manifest is not rewritten

`tests/fixtures/literature/lct-enattah-2007/searches.tsv` is byte-identical to `main` and does not
appear in the diff. Re-deriving a manifest from a re-capture changes `search_id` by construction,
because the id hashes `(database, query, executed_at)`, so superseding a published manifest version
is a data revision rather than a backfill. It is tracked in #272.

The consequence, stated because it is not tidy: `searches.tsv` (37 rows,
`lct-rs4988235@2026-09-06.1`) and `searches.pending.tsv` (70 rows, `lct-rs4988235@2026-09-12.1`)
describe different captures and share no identifier. A test asserts the disjointness so neither file
can be read as the other's revision, and the two `included` decisions are exactly as merged.

## The finding

Re-executing the three queries: Q1 (11) and Q2 (1) reproduce the merged candidate sets exactly. Q3
does not. The merged manifest recorded 25 candidates while the query matches 58, and those 25 are
exactly the set PubMed returns with `retmax=25`, so the merged capture was truncated at 25 and
nothing recorded the cap. `scripts/fetch_pubmed_manifest.py` fetches with `retmax=100000` and
rejects that disagreement, so the merged file could not have come from the documented tool. All
three counts were re-checked against PubMed today and are unchanged.

`evidence.tsv` and `field_evidence.tsv` are untouched: the builder reproduces them byte-for-byte,
and all 12 `source_record_id` values re-derive through `make_source_record_id`.

## Provenance

`executed_at` is a recorded execution rather than the merged manifest's value, so the record no
longer asserts a capture date it denies. Each committed payload reproduces byte-for-byte on a fresh
execution of the same query; that was checked against the live server before committing rather than
asserted in a docstring. Payload hashes are in the audit doc.
