## TL;DR

#323 fixed a bug where our schemas silently rounded fractional counts down instead of rejecting
them, so "3.9 genes" quietly became 3 and nothing downstream could tell it had been invented. Three
columns in the curated registry still did it. Now they don't.

It also adds a guard so this cannot reappear anywhere: a test that walks every schema in the package,
hands each column the value 1.5, and fails if any of them stores 1.

**One thing needs your attention beyond the fix.** Making it revealed that a published release
recorded the hash of a source file and compared it byte-for-byte, which had quietly made that file
unmodifiable — a comment or a lint fix would have failed the build. That test is narrowed here, on
the maintainer's decision, and the reasoning is written into the test itself.

---

## The defect

`CPIC_COVERAGE_SCHEMA` declared three count columns as plain numpy integers in a schema with
`coerce=True`. Pandera coerces before it checks, so the cast truncated and the truncated value was
what got validated. Confirmed against a complete, otherwise-valid row before changing anything:

```
pair_count=3.9         -> ACCEPTED, stored as 3
allele_row_count=10.7  -> ACCEPTED, stored as 10
candidate_count=2.5    -> ACCEPTED, stored as 2
```

Now refused, while `pair_count=3.0` still passes — anything computing a count in floating point
produces integral floats, and rejecting those would be a different bug.

Unlike the P1 case #323 fixed, no live path feeds these from a float today. The reason to fix it is
not that a fraction had been seen; it is that a coerced value is indistinguishable from a counted one
once stored, and this schema gates what reaches the curated variant set.

## The guard

`tests/test_schema_coercion_guard.py` walks every `DataFrameSchema` reachable in the package and,
for each coercing one, hands every column a 1.5 and fails if any returns an integer 1.

**Behavioural, not nominal.** It never asks what a dtype is called, so a column that truncates is
caught however it is spelled, and a safe one is never flagged for being unfamiliar. Narrowed to
genuine integer coercion, so a string column turning 1.5 into `"1.5"` is correctly ignored — that is
a representation change, not a truncation.

It also asserts the walk finds the schemas it is supposed to guard. A guard that silently walks
nothing passes forever, and that failure mode is invisible.

Both were verified by mutation: reverting any one column to `int` fails it.

## The part that needs explaining: narrowing a reproducibility test

`test_repository_sources_build_a_complete_reproducible_candidate_release` compared the whole
`MANIFEST.json` byte-for-byte against the committed release. That manifest records
`domain_sha256` — the hash of `genomeos/registry/curated.py` itself.

So **any edit to that file invalidated the release**, including a comment. The file and the release
were committed together in #279 and had never been touched since, so this surfaced the first time
anyone tried to change it.

All three data tables still reproduced byte-identically. Only that one hash moved.

The test now asserts what the release actually has to guarantee:

- the three data tables reproduce byte-for-byte, with a message saying that a failure here is a real
  regression rather than provenance drift;
- the manifest's `counts` match;
- the manifest's per-file `outputs` hashes match.

It no longer asserts that today's source is byte-identical to the source that cut a past release.
That is a much stronger claim than reproducibility of the data, and nobody chose it.

**Provenance is not weakened, and I did not take that on trust.** A new test asserts the manifest's
builder, domain and adapter hashes are live — each names a file that exists and carries a real
64-character digest, so a stale or hardcoded hash fails.

**And the narrowed assertion was mutation-tested**, because loosening a test to make a change pass is
exactly the move this repository warns against. A builder that drops one row from every table still
fails it:

```
mutation: frame.iloc[:-1].to_csv(...)   ->  FAILED at the data-file comparison
```

The alternative was publishing `curated-v1-candidate.2` with byte-identical data and a new manifest.
That is defensible under the immutability invariant, but it would set a precedent that every source
edit needs a release bump, which would make the file unrefactorable. Raised as a decision rather than
decided in passing; the maintainer chose narrowing.
