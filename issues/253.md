### canderson50, 2026-10-19T17:25:28Z (https://github.com/genomeOS/genomeOS/issues/253#issuecomment-6273111763)

I looked into where a native local filesystem could come from. Short version: standard RunPod pods probably can't provide one, but most VM-based GPU clouds can, because their local NVMe arrives as a raw device that you format ext4 or xfs yourself.

### RunPod

- **Standard pods.** The docs describe the container and volume disks as "fastest (local)" ([storage types](https://docs.runpod.io/pods/storage/types)), but your two Secure Cloud A100s showed `/workspace` on MooseFS over FUSE, with an overlay root. RunPod's engineering blog confirms MooseFS backs its network storage ([model store post](https://www.runpod.io/blog/building-runpods-model-store)). I found no pod-creation setting for filesystem type, which matches what you concluded here, so "local" in the docs seems to describe performance rather than a placement guarantee.
- **Bare Metal.** Dedicated servers with full OS control and up to 2 TB NVMe, A100 80GB among the options ([bare metal](https://www.runpod.io/gpu-bare-metal-server)). That would satisfy the runner, but it's a months-to-years reservation, not on-demand.

### VM-based alternatives (hourly or per-second)

| Provider | Single A100? | Local storage | Notes |
|---|---|---|---|
| Google Cloud A2 | yes (`a2-highgpu-1g`) | Local SSD, a raw NVMe device; format and mount it ([Local SSD](https://docs.cloud.google.com/compute/docs/local-ssd), [setup](https://docs.cloud.google.com/compute/docs/disks/add-local-ssd)) | GPU quota request; data lost when the VM stops |
| AWS p4d / p5 | no (8-GPU only) | 8 × 1 TB / 8 × 3.84 TB instance-store NVMe ([p4d](https://aws.amazon.com/blogs/compute/amazon-ec2-p4d-instances-deep-dive)) | P-instance quota starts at 0 for new accounts |
| Lambda Cloud | yes | ephemeral NVMe per node (third-party docs; filesystem type not published) | avoid its network filesystems for this |
| Hyperstack | yes | ephemeral virtual disk `/dev/vdb`; NVMe passthrough only for contracted customers in CANADA-1 ([local NVMe](https://portal.hyperstack.cloud/knowledge/local-nvme-storage), [ephemeral](https://docs.hyperstack.cloud/docs/storage/ephemeral)) | cheapest A100 listed |

### Two points for the admission decision

1. **A VM's boot disk might already pass.** The runner checks filesystem type (ext4/xfs/btrfs) plus its own probes, and a stock Ubuntu VM root is usually ext4 on a virtual block device. Is that "native local" in this issue's sense, or should it be the local NVMe specifically? The NVMe route is the unambiguous one. Either way, per this issue, the `findmnt` evidence on the actual instance decides, not the provider's label.
2. **Keep write-cache flushing on.** GCP's Local SSD guide mentions an optional mount setting that skips flushes for speed. That would undermine the fsync and commit/readback probes, so it shouldn't be used here.

Nothing here has been tested on a live instance; it's from provider documentation. Which route would you consider?
