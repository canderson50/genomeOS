## Body

## Scientific objective and dependency

Supply the actual supported execution/storage substrate for the already frozen B0H calibration in #211 / PR #252. No scientific change or new model is requested. The runner's native-local-filesystem refusal is deliberate, not a bug to bypass. This operational qualification is required before the first full calibration can start.

## What was observed

At source `e20aed4b3ec199fc5d9960b8cdc804f264ffebd3`, the full suite passed 1,854 tests (17 skipped, 15 baseline Rasterio warnings); final whole-branch review had no Critical or Important findings.

Two actual single A100-SXM4-80GB Secure Cloud placements were obtained in US-MD-1 and US-KS-2. Both used `runpod/pytorch:1.0.2-cu1281-torch280-ubuntu2404`, 80 GB container disk and a 1,200 GB persistent volume. Create/get responses explicitly identified `mounts.persistent`; no network volume was requested. Both GPUs were healthy with 81,152 MiB free.

On each pod, this read-only command:

```text
findmnt -T /workspace -o TARGET,SOURCE,FSTYPE,OPTIONS,AVAIL,SIZE -b
```

reported an `mfs#<datacenter>.runpod.net:9421[...]` source and `fuse` filesystem. The observed root filesystem was overlay; available native-local filesystem binds were individual system/Nvidia files rather than usable campaign directories. Provider labels did not establish the required storage behavior/locality.

Both created GPUs were stopped, their volumes retained, and no setup/admission/null simulation/scientific START occurred. A bounded same-SKU Community request across all 11 preferred US/CA datacenters returned 400/no matching instance: it supplied no Community filesystem evidence and does not establish global GPU unavailability. A broader datacenter-GPU hardware pool is under pre-START review, with unchanged science and storage guards.

## Expected output and acceptance evidence

- Actual Linux campaign directory on an admitted native local filesystem, with mount/source/options evidence and the declared free-space reserve; cloud labels alone are insufficient.
- Existing cross-process exclusion, SQLite DELETE/EXTRA/FK, commit/readback, rollback and directory-fsync probes pass on that directory.
- Exact reviewed source and locked runtime; one actual JAX/CuPy GPU with float64, unchanged frozen manifest, seeds, count cases, backend, retry and statistical gates.
- A one-shot operational invocation and a verified external closed collection; no known-result redelivery or automatic replacement campaign.

These are platform-admission criteria, not calibration success. The full scientific accounting and controls still determine eligibility later.

## Component, constraints and next actions

The existing public boundary is `scripts/run_b0h_calibration.py admit` and `heterogeneity_runner_admission.observe_b0h_admission`; the current mount allowlist is ext4/xfs/btrfs/tmpfs, with tmpfs explicitly excluded by this full-campaign launch policy. No current source change has been made.

The public REST v2 contract offers `mounts.persistent` but no filesystem-type/non-FUSE placement constraint; its datacenter catalog does not describe native backing. Prefer actual compatible placement over code changes. If a pre-case admission correction is proposed, it requires a separately explicit design, evidence, implementation and review, as anticipated in the committed runner plan's Task 5 admission note. Do not silently accept overlay, MFS/FUSE, fake mount evidence, shared host-device manipulation, or volatile memory storage.

This is distinct from optional query optimization #251 and optional multi-GPU scheduling; neither is a prerequisite to the first single-GPU study. Consumers are the immutable calibration evidence and later unchanged B0H/B0 comparison, not serving or surface promotion.
