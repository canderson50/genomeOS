## Body

## Scientific objective / invariant

A cited registry version must identify stable population-coordinate evidence. Atlas design §12 explicitly requires a registry version bump when coordinates change, so old surfaces remain valid and citable. The standalone registry publication in #23 also requires stable identity. This is an existing P0 build behavior found during #189 WP0 / #21 / #219 work, independent of the explicit HGDP support fix.

## Reproduction

Tested the committed `scripts/build_registry.py` and its seven package/source dependencies at `3c986902c12b40b84c56145ed863f7f519cbab6b`. The source copies and both before/after Parquet snapshots were retained locally with SHA-256. Only disposable synthetic inputs and outputs were used; no existing registry, published surface or real source record was changed.

Create two TSVs with the following header and one fictional row each:

```text
population\tlatitude\tlongitude\tuncertainty_radius_km\tprovenance
```

The first row is `Example`, latitude `1`, longitude `2`, radius `2.5`, provenance `synthetic:overwrite-audit#row-1`; the second differs only in latitude, which is `3`. The tab notation above means actual tab separators. The explicit support columns are ignored by this old adapter, a separate issue already tracked under #21/#219.

From a checkout at the tested revision, using a new disposable output path:

```sh
PYTHONPATH=. python scripts/build_registry.py --hgdp first.tsv --out scratch-registry
PYTHONPATH=. python scripts/build_registry.py --hgdp second.tsv --out scratch-registry
```

Both calls exit zero and print `registry v0.1.0: 1 populations, 1 aliases`. The second replaces `populations.parquet`: latitude changes from `1.0` to `3.0` while `registry_version` remains `0.1.0`. The aliases are unchanged.

Retained population-file SHA-256 values:

- Before: `8586a679ee4d16e2f0d535fcd953fdf00fdc4162957e3bb49a19e8acced903a5`
- After: `5425de7ddf2b6f56d660477c784e3e8724a30106e0ed66ff020781c9653e3dc7`

`VERSION` is hard-coded and `args.out.mkdir(parents=True, exist_ok=True)` permits reuse before both Parquet files are written. This reproduction establishes overwrite and same-version content changes; it does not establish that a published registry has been affected.

## Expected behavior and acceptance evidence

The engineering component is the offline P0 registry build CLI and its immutable output contract. Existing output content must not be silently replaced; a content-changing registry build must receive a distinct, explicit identity. Determine the version/content-fingerprint policy before implementation so that merely choosing another directory cannot create conflicting artifacts with the same claimed identity.

Acceptance should include:

- A synthetic repeat-build test demonstrating refusal before changing any existing output byte.
- A changed-coordinate/support input producing a newly identified registry, with the previous artifact preserved.
- Provenance binding the registry identity to its consumed inputs and generated files.
- An explicit decision and tests for partial output/failure handling; two independently written Parquet files must not masquerade as one complete release.

Schema-valid records do not establish source qualification, and this fix must not manufacture missing coordinates, radii, provenance or review. Downstream consumers are P1 joins, P2 provenance and the citable registry release. Keep this separate from #21/#219 so the current input-boundary fix does not expand into publication/version management.

Open and closed searches for `registry overwrite`, `registry version`, `"build_registry.py"`, and `"immutable" "registry"` found no duplicate. All four label families are supplied.
