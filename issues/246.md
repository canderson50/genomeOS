## Body

Follow-up from #207 and #193, split out so #193 keeps its open questions rather than being closed by the merge.

#207 ships one reviewed AVI cache readout for rs334 as an annotation tab, with no API key and no runtime dependency. Two questions are deliberately left unsettled there.

## 1. Acquisition path

The AlphaGenome terms permit commercial use for "AVI Scores and other artifacts that are made available for download within the 'Permissive Use Downloadable Artifact' section of the AlphaGenome Services website". The carve-out is worded against the download artifacts, not against an AVI value however it was obtained.

The committed payload records `AlphaGenome (Avsec et al. 2026); Atlas AVI, accessed 2026-09-09`, which is a read through the Atlas interface rather than the bulk download. Sourcing the score from the permissive download is the low-risk path. `alphagenome@google.com` is the contact the terms name for written confirmation. This is a maintainer terms call, not something the contributor can settle.

## 2. Refresh cadence

Live refresh would need an AlphaGenome API decision (the free API is non-commercial) and a stated cadence for re-fetching.

Related and worth stating explicitly: pinning the model version in the payload means a recompute cannot silently change a cited readout, but it also means a stale cache is only visible if something checks the version against the source. Nothing does that check today.

## Licence reading

`docs/audits/alphagenome-avi-licensing.md` in #207 records the verbatim terms, what is published and what is not, and why the per-feature attribution breakdown cannot be redistributed while the score can.

**1. Finding.** I compared the two acquisition paths against each other on one variant, rs334. They return the *same* score: reading GRCh38 chr11-5227002-T-A through the Atlas interface and running the AlphaGenome inference API both give avi_phred 11.77, avi_tail_quantile 0.0665, dominant modality AlphaMissense — the values already pinned in the #207 payload.

**2. Contradiction.** The two paths differ only in what *else* comes back. The Atlas read returns the AVI Score and its identifying metadata. The inference call returns those **plus the per-feature attribution breakdown**: `top_feature_importance`, `fi_ALPHAMISSENSE`, `fi_MERGED_SPLICING` and roughly twenty further per-feature fields. That is the field set `docs/audits/alphagenome-avi-licensing.md` records as outside the AVI Score and not redistributable.

**3. Hypothesis.** If that is right, the acquisition-path question is not only a risk ranking between two routes to the same number — it decides whether the restricted field enters the repository at all. Sourcing from the Atlas interface or the Permissive Use download keeps it out by construction; the inference API brings it in on every call, which then relies on the `KNOWN_NON_COMMERCIAL_FIELDS` gate catching it. I am not proposing we choose on this basis; it just seems worth having in view when the call is made.

**4. What I opened.** The Atlas interface for chr11:5227002:T>A, and the AlphaGenome inference API for the same variant run locally through the Antigravity science skill (53 packages installed outside the tree; no key in the repository; output written to a scratch directory and not committed). Also `docs/audits/alphagenome-avi-licensing.md` and the #207 payload. I checked the repository tree for any occurrence of the breakdown fields: clean. The only mentions of `top_attributions` are prose about the gate, in `docs/non-commercial-data.md` and the audit.

On the second half of this issue — the stale-cache check that nothing does today — I built one outside the tree and ran it against the pinned value. It reports `CURRENT` when the pin matches at the pin's recorded precision and `DRIFTED` otherwise. Two things it measured. The committed rs334 payload was retrieved `2026-09-09` and was **29.7 days old** at my check on 2026-10-08, so it is at about a month now and the age only grows — the exact figure is whichever day you read this. And the two acquisition paths do not disagree, so a refresh is not currently urgent on value grounds. I am not opening a PR for it while #310 and #403 are both waiting on you; it is here as evidence for whatever cadence you want, and I would rather take your number than propose one.

**5. Implication for the atlas.** The pinned AVI is verified against the live source through both paths, so the number on the panel is sound. The open question is provenance, not accuracy: the payload records a read through the Atlas interface, and an API-sourced value would need to say so in the same field, because that is the distinction the carve-out is worded against.

**UNIVERSAL:** both ways of asking give the same number, but only one of them also hands back the part we are not allowed to republish — so where we fetch from decides what we are holding.
