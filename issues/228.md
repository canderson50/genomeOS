## Body

## The decision

Should an AFND `source_record_id` hash an **explicit canonical numeric format** for the
frequency, rather than whatever `str()` of the parsed float produces?

This came out of the open question on #160. The narrow safety problem is already fixed in
#229 — no NumPy scalar reaches the hash any more, so no dependency on NumPy's formatting
remains. What is left is a genuine design choice with a migration cost, which is why it is a
decision rather than a task.

## The three options

**A. Status quo, hardened (what #229 ships).** Hash `str()` of a native Python float.
`str()`/`repr()` of a float has been the shortest round-tripping string since Python 3.1,
computed from the IEEE-754 bit pattern, so it is platform-independent. Parsing first means
AFND's thousand separators and trailing zeros cannot change an id: `"0.2500"` and `"0.25"`
hash alike (verified).

**B. Hash the raw 4-dp string as printed.** Canonical at the source, but *loses* the
formatting-drift protection: `"0.2500"` and `"0.25"` produce different ids (verified —
`71f74ff2…` vs `9f6b813f…`). A cosmetic change in an AFND release would re-mint records. This
looks like the safe option and is the worst of the three.

**C. Hash an explicit fixed format, `f"{af:.4f}"`.** Keeps the drift protection
(`f"{0.2500:.4f}" == f"{0.25:.4f}"`) and removes any reliance on shortest-round-trip
formatting, since the format-spec mini-language is not the repr algorithm. It also states the
source's published precision instead of leaving it implicit.

## Why it needs a decision rather than a commit

Option C **re-mints every `afnd-frequencies` identity**. Verified:

```
str(0.125)     = '0.125'   -> afnd-frequencies:7cd70a92...
f"{0.125:.4f}" = '0.1250'  -> afnd-frequencies:6bf5babd...
```

That collides with the immutability invariant (§5, AGENTS.md): "Artifacts are immutable, keyed
by `(variant_id, model_version, data_version)`. A model change publishes new artifacts; it never
mutates a map someone has cited." So C is only reachable through a deliberate `data_version`
bump with republication, not a quiet change. Anything already citing an AFND record id would
stop joining.

## Recommendation

**Stay on A for now, and adopt C only when a `data_version` bump is happening anyway.** The
residual risk A carries is not zero but it is dormant and now guarded: #229 adds a test
asserting the two scalar forms hash alike, so a `str()`/`repr()` swap or a NumPy formatting
change fails by name rather than silently. C's advantage is self-description, which does not
justify breaking existing ids on its own.

The one thing that would change this: if AFND ever publishes **more** precision than 4 dp, C
would silently truncate and merge two genuinely distinguishable measurements, while A would
keep them distinct. That argues for A on scientific grounds too, and means C should really be
`f"{af:.4f}"` *plus* a refusal when the parsed value carries more precision than the format
preserves. Worth settling before adopting C.

## What is already done

- #229 removes the NumPy dependency from the identity in both adapters and pins both digests.
- The drift-protection and scalar-form claims above are all empirically verified, not inferred.

## What this issue needs

A person to commit on the project's behalf, since it trades a citable-identity break against
self-description. No code change should land against this until that call is made.

## Measured against the real corpus. Option C would corrupt data, and no migration is needed.

I ran the audit before implementing, against `data/raw/afnd_frequencies.tsv` (123,502 rows) and the real adapters. Three findings, each of which changes the answer.

**1. Option C collapses genuinely distinct measurements.** The premise that AFND is canonical at 4 dp is wrong for the actual data. **10,040 rows carry more precision than 4 dp** — all HLA, rare alleles printed to 7 dp. Under `f"{af:.4f}"`:

```
0.0000980 vs 0.0000900  ->  '0.0001' / '0.0001'   collide: True
0.0000050 vs 0.0000020  ->  '0.0000' / '0.0000'   collide: True
```

Two different observed frequencies become one identity, so `unique=True` rejects both. Worse, a real observed rare allele formats to `0.0000`. Under `str()` neither pair collides. This is the scientific wrinkle flagged in the original issue, and it is not hypothetical — it is 8% of the corpus.

**2. There is nothing to migrate: the published identities already match current code.** Every published AFND observation id still mints identically today.

| dataset | published ids | matching current | |
|---|---|---|---|
| hla-dqb1-03-01 | 406 | **406** | 100% |
| hla-a-02-01 | 278 | **278** | 100% |
| hla-drb1-15-01 | 416 | **416** | 100% |
| kir-2dl1 | 233 | **233** | 100% |
| kir-3ds1 | 235 | **235** | 100% |

Across 28 AFND-derived datasets, 7,292 published observations carry an id, all at `data_version=afnd-2026-08`. They were built after #131/#161 widened the key, and #160/#227 preserved ids exactly, which the pinned digests prove.

**3. The new refusal changes no published number.** **Zero rows** in the real corpus have a non-integral sample size, so `fractional_sample_size` (#160, #227) is a guard against future releases, not a correction of existing data. Full run of current code on the real corpus is clean: frequencies retain 88,351 of 123,502 with exactly **1** `duplicate_source_record`; carriers retain 3,348 of 3,790; cytokines 1,243. No fractional refusals anywhere.

## Recommendation: close as not planned

Option A is not merely the cheaper choice, it is the correct one. `str()` of a Python float is already the shortest round-tripping canonical form, so it is lossless at any precision AFND publishes. Option C trades that correctness for self-description. Option B was already the worst, losing drift protection.

#229 completes the only real improvement available here: it removes the dependency on NumPy's scalar formatting, so the identity rests on CPython's float formatting alone, with a test pinning the invariant. Nothing further is worth doing.

`afnd-cytokines` was never affected either way — its key is `(locus, population)` with no numeric part.

Leaving this open rather than closing it myself, since it is labelled `needs-human-decision`.

**Decision (@bschilder): no. We do not want to throw away any precision.**

That rules out option C as specified. `f"{af:.4f}"` discards real precision in 10,040 rows and collapses distinct measurements onto one identity, so it is rejected on scientific grounds rather than on migration cost — the cost was never the deciding factor.

Option A stands, and is already the lossless choice: `str()` of a parsed Python float is the shortest round-tripping representation, so it preserves whatever precision the source publishes, at any precision, while still making `"0.2500"` and `"0.25"` hash alike. #229 completes it by removing the dependency on NumPy's scalar formatting.

Closing as not planned. Reopening this needs an argument that survives the 10,040-row finding above.
