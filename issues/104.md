## Body

Two separate GPU stories, with different payoffs. Worth keeping them apart, because the obvious one is not the one that matters most today.

## 1. The fits — JAX, already landed

The spherical HSGP has a few hundred basis coefficients, and PyTensor's Python-level loop dominates the runtime:

| sampler | 332-survey HbS fit |
|---|---|
| PyMC default | **did not finish in 20 minutes** |
| `numpyro` (JAX, CPU) | **15 s** |

`FitConfig.nuts_sampler` now defaults to `numpyro`, so this is done on CPU. **The same code path runs on a GPU with `jax[cuda]` and no model changes** — `pm.sample(nuts_sampler="numpyro")` picks up the device automatically.

That matters for #40: P2 fits one surface *per variant* across the curated set. The fits are embarrassingly parallel, so the batch story is "many small JAX fits", and a GPU pod is the natural host. Per repo convention, prefer US-East/Central datacenters.

## 2. The geospatial joins — cuSpatial, not yet

[cuSpatial](https://docs.rapids.ai/api/cuspatial/stable/) is CUDA-only, so this is a Runpod-side path, not something that runs on a Mac. Two concrete targets, not a general "use RAPIDS":

**#43 — raster to H3.** The global WorldPop 1 km mosaic is ~933M pixels, and `aggregate_raster_to_h3` currently does a Python-level H3 lookup per populated pixel. Being precise about what helps: **cuSpatial does not implement H3**, so it does not solve this directly. The honest easy win here is [`h3ronpy`](https://pypi.org/project/h3ronpy/) — a Rust/Arrow H3 implementation with a vectorised numpy API — which should collapse that loop on CPU. cuSpatial's contribution would be the surrounding windowing and coordinate work, not the indexing.

**#94 — assigning H3 cells to countries.** This *is* a cuSpatial-shaped problem: `quadtree_point_in_polygon` over a global cell set against GADM/Natural Earth polygons. At res 6 that is millions of point-in-polygon tests, which is exactly what the quadtree join is built for. `cuspatial.haversine_distance` would also cover the mask's cell×observation distance block, though that is already chunked numpy and is not currently a bottleneck.

## Ordering

The sampler was the bottleneck and is now handled. cuSpatial is worth adopting when #43 runs on the real global raster and #94 needs res-5/6 country assignment — not before, since a CUDA-only dependency in the offline path is a real cost to contributors without a GPU.

Related: #40, #43, #94, #49.

### bschilder, 2026-08-25T21:59:48Z (https://github.com/genomeOS/genomeOS/issues/104#issuecomment-5417388040)

**Half done: JAX-on-GPU is working and measured. cuSpatial is untouched.**

Confirmed on an A100 pod: `JAX DEVICES: [CudaDevice(id=0)]`, and numpyro picks the device up with no model change. A held-out cross-validation run is executing on GPU now.

**A caution worth recording before anyone optimises further.** GPU is not automatically the faster choice for this model. `gpu_check.py` measured **18×** on a 1500×1500 Cholesky, but at the M we actually use (150–200) the matrix has ~100× fewer elements and kernel-launch overhead dominates — and NUTS is a long *sequential* chain of small ops, the workload GPUs are worst at. A related finding from #108: a fit at M=400 on a fully-utilised A40 took **80 minutes** while M=200 on a laptop CPU took **8.8**, because inducing points spaced far inside the correlation range make `K_uu` near-singular. That was a conditioning problem misread as a hardware one.

So: GPU earns its cost at large M or with many vectorized chains, and a **CPU pod is likely the better price/performance point** for fits at the current M. cuSpatial's case should be argued on the geospatial joins (H3 assignment over raster pixels in `geo/population.py` is a per-pixel Python loop and is the real candidate), not on the fits.

Leaving open for cuSpatial.
