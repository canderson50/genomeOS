## Body

Golden test 1 (#45) now has both reference halves and a scorer:

- **input** — 332 real MAP HbS surveys, 64 countries (#91)
- **target** — Piel et al.'s 191 national estimates with IQRs (#93)
- **scorer** — §8's three criteria, in `genomeos/validation/hbs_parity.py`

The missing middle is turning a fitted surface into **one AS/SS neonate estimate per country**, which is what the scorer consumes.

## Why this is not a one-liner

The obvious shortcut is to evaluate the surface at a country centroid. That would be worst exactly where it matters: Nigeria, India and the DRC carry most of the global burden and are precisely the countries whose internal HbS variation is large. A centroid value for India is not a number anyone should score parity against.

Piel's approach, and the one §9 already specifies, is population-weighted:

> Cell population from WorldPop 100m (fallback GPWv4 30 arc-second), aggregated to H3. Births = cell population × national crude birth rate (UN WPP)

So: predict per H3 cell → weight by cell population → sum births × affected frequency within each country's boundary.

## What it needs

1. **Country boundaries** — GADM or Natural Earth, joined to H3 cells. Overlaps #61, which needs the same rollup for the admin choropleth, so the two should share one implementation rather than each growing their own.
2. **A gridded population denominator** — #43.
3. **Crude birth rates** — already available per country in the committed Piel reference table (`crude_birth_rate`), so UN WPP is not a blocker for the parity run specifically.
4. **Country name reconciliation.** The scorer joins on country name, and the three sources spell them differently — the MAP export has "United Republic of Tanzania", Piel's table has its own conventions, GADM has others. This wants ISO3 codes throughout rather than name matching. Cheap to do now, expensive to retrofit once three call sites depend on names.

## Note on masked cells

Aggregation must exclude `unknown` and `prior_dominated` cells and report the unmapped fraction (§10, #38 already implements this). A country that is mostly unmapped should not silently produce a confident national total — and for parity that matters, because Piel had survey coverage we do not.

Related: #45, #43, #61, #92.

### bschilder, 2026-08-24T22:40:13Z (https://github.com/genomeOS/genomeOS/issues/94#issuecomment-5402456577)

**On implementation: this is the one genuinely GPU-shaped step in the pipeline** (context: #104).

Assigning H3 cells to countries is a point-in-polygon join. At res 4 that is ~288k cells against ~177 country geometries; at res 5/6 it is millions. [`cuspatial.quadtree_point_in_polygon`](https://docs.rapids.ai/api/cuspatial/stable/) is built precisely for that shape and would be the right tool if this becomes slow.

Two practical notes:

- **CUDA-only**, so it belongs behind an optional extra and a CPU fallback, not as a hard dependency. Contributors without an NVIDIA GPU still need to be able to run the country rollup.
- **Start on CPU and measure.** `matplotlib.path.contains_points` with a bounding-box prefilter already does the 22k-point land mask in 0.01 s (`genomeos/viz/basemap.land_mask`), and the same prefilter approach scales a long way before a GPU is warranted. The geometry is also already committed as `reference/ne_110m_countries.geojson` with `iso_a3` codes — which is the join key this issue needs anyway, to avoid the "United Republic of Tanzania" name-matching problem across MAP, Piel and GADM.

So: land/country geometry and an ISO3-keyed join exist now; the GPU path is an optimisation to reach for when res-5/6 assignment is the measured bottleneck, not a prerequisite.
