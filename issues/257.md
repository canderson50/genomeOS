## Body

## TL;DR

The design document for our variant lookup table says certain bad entries should be rejected — a made-up date, a reviewer name in the wrong format, a source with no version number. The code does not actually reject them; all of those were tried and accepted. Some of these are worth enforcing in code. Two of them a computer genuinely cannot judge, and pretending otherwise is worse than admitting it, because a reviewer who thinks the machine checked will not check themselves.

---

## What

The variant-normalization registry's design (`docs/superpowers/specs/2026-09-10-variant-normalization-registry-design.md` §5) states refusal conditions that `genomeos/registry/variants.py` does not enforce. Each was exercised during the final whole-branch review and **accepted**:

| Value | §5 says | Today |
|---|---|---|
| `resolved_at = "yesterday"` | UTC timestamp | accepted |
| `resolved_at = "2099-01-01T00:00:00Z"` | "or in the future" | accepted |
| `reviewed_by = "me"` | `human:<slug>` or `agent:<provider>:<model>` | accepted |
| `reference_resource = "dbSNP"` | "Named **and versioned**" | accepted |
| `printed_convention = "-174"` | "a bare number with no stated convention" refuses | accepted |
| `chr1-100-A-A` | (implied) a substitution | accepted — `ref == alt` |

## The split I would make, rather than enforcing all of them

**Enforce in code** — cheap regexes on pure-provenance fields a human will trust without re-deriving:
- `reviewed_by` format. An identity that does not parse cannot be audited, and the whole extractor-versus-verifier discipline rests on it.
- `resolved_at` being a real UTC timestamp and not in the future.
- `ref != alt`, since a registry of substitutions should not accept a non-substitution.

**Do not pretend to enforce** — these are judgements a machine cannot make:
- whether a `reference_resource` is genuinely "named and versioned"
- whether a `printed_convention` states a convention rather than a number

A regex here would check for a digit somewhere and pass `"dbSNP 1"`. **Leaving them looking enforced is worse than stating them as reviewer duties**, because a reviewer who believes the schema caught it will not check. Move these two from §5's refusal table into an explicit reviewer checklist, in the spec and in the audit template.

## Why this matters more than it looks

The one case that bit in practice: the HbS row shipped with `reference_resource = "identity row; no external resolution required"` while asserting `rsid: rs334` — a real external claim with no source named. `validate_rows` accepted it because the check is "non-empty string". Fixed in the branch by naming the actual resources, but nothing would have caught a repeat.

## Also worth considering: an explicit `row_kind` column

The identity-row exemption (a row whose `variant_id` already equals its `normalized_variant_id` needs no verification) currently keys off that structural coincidence rather than a declared kind. It is the smallest correct implementation and is commented, but it would apply silently if an adapter ever minted an internal id that coincidentally equalled a coordinate without being one.

Worth a column only if that case becomes real — AGENTS.md says to wait for two consumers. Filing so the reasoning is not lost.

## Acceptance evidence

- Each enforced condition has a test asserting refusal, and a test asserting the valid form passes.
- The two unenforceable conditions appear in a reviewer checklist, and §5's table no longer implies the schema catches them.
- Existing rows still validate.
