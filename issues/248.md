## Body

## TL;DR

When someone sends us new data, they have to wait for a maintainer to sit down and check it by hand. Most of what that check finds is mechanical — numbers that do not add up, a count that is wrong, an identifier that does not match. A script can catch all of it the moment the contribution arrives, for free, and tell the contributor straight away. This proposes building those automatic checks. The one to start with is a totals check, because two different people got the same total wrong in a row.

---

## Why

Four data PRs were reviewed on 2026-09-10 (#156, #160, #188, #207). Sorting what the review found by whether a script could have caught it is stark: **most of it was mechanical**, and one defect appeared in two consecutive PRs from two different contributors.

The motivation is contributor self-service — feedback at PR time rather than whenever a maintainer next sits down with an agent.

## What a script can own

Each of these is deterministic, needs no model, no API key, and no secret:

| Check | Evidence it was needed |
|---|---|
| Coverage totals reconcile against the manifest | **Failed in #156 and #188** — the audit doc's stated counts did not add up against the actual rows |
| Exactly 19 field-evidence rows per record | Currently asserted per-corpus in bespoke tests |
| Identifiers recompute from `make_source_record_id` / `make_search_id` | Verified by hand in review each time |
| Every `derivation_method` is on the closed allowlist | Verified by hand |
| Committed payloads replay to the committed manifest | #188 added this per-corpus; it should be generic |
| A bespoke fetcher where the documented tool exists | #188 reimplemented `fetch_pubmed_manifest.py`; #156 shipped no builder (#237) |
| A coordinate-keyed external resource on a non-coordinate id | #207; superseded by the registry in #247 |
| Screening decisions separated from discovery | #188 fused them |

## What a script cannot own

Reserve these for a model, later, and only these: whether a locator points at the right table (#156's real defect), whether transcribed counts match the source, and whether a licence covers the specific artifact being stored (#207's real defect).

## Design constraints, both learned today

**Fork safety.** Every data PR so far came from a fork — #156, #188 and #207 from one contributor, #160 from another. So the checks must run under `pull_request` without secrets. The safe pattern is **trusted code over untrusted data**: check out the scripts from `main`, read the contributor's data files, and never execute anything from the fork.

**Prompt injection is the reason to keep the model layer last.** GitHub blocks its own automations from acting on events from users without write access, explicitly to prevent untrusted PR content reaching a model that then acts with repository authority. A data PR is largely contributor-authored prose — audit documents, `notes` fields, commit messages. Any model layer must treat that strictly as data, never as instruction, and stay advisory rather than gating. **The mechanical checks carry none of this risk**, because nothing they read can influence what they conclude.

## Suggested first step

Just the coverage-reconciliation check. It is a few lines, it failed twice, and it needs nothing else to exist first.

## Acceptance evidence

- A PR whose audit doc counts disagree with its manifest fails CI, naming both numbers.
- The check passes on the two corpora currently on `main`.
- It runs and reports on a PR opened from a fork.
- No secret is required for any check in the first tranche.

## Not in scope

The model layer, and any dependency on a specific vendor's agent product. GitHub Copilot automations are unavailable in public repositories, so that route is closed here regardless.
