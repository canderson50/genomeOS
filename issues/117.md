## Body

Follow-up to #18, which landed the P0 registry adapter (`genomeos/registry/sources/afnd.py`). Two things it deliberately could not do.

## 1. Get the corpus — this is the blocker, and it is a permission conversation

Checked 2026-08-25 while implementing #18:

- **AFND publishes no licence.** The site footer's "Licensing" link resolves to [`contact.asp`](https://www.allelefrequencies.net/contact.asp), which carries only a Disclaimer and a Privacy Policy. Pages are marked "©2003-2026 The Allele Frequency Net Database". [re3data](https://www.re3data.org/repository/r3d100011904) records the repository as public domain, but that is third-party catalogue metadata, not a grant from AFND.
- **There is no bulk download.** The only documented programmatic route is "Automated Access" ([`extaccess.asp`](http://www.allelefrequencies.net/extaccess.asp)) — a URL-parameter convention for *linking a search* from an external website, conditioned on "If you are using this facility please cite our database in your website". It returns rendered pages, not data files.
- **Frequency data is session-gated.** Fetched without a login, a population page's Allele/Haplotype Frequencies section renders `Access Denied. Your session has expired or you have not logged in yet.`
- Population *metadata* renders publicly at `pop6001c.asp?pop_id=N`, one page per population, with no export.

AGENTS.md requires the licence to be checked before ingesting and names AFND in the open redistribution question (#66), so #18 did not harvest the corpus, ships no fetcher, and has **never been run against the real 1,324 populations**. There is a scraped third-party mirror ([slowkow/allelefrequencies](https://github.com/slowkow/allelefrequencies), MIT on the *code*) — it carries no coordinates, and its existence does not change AFND's terms.

**The ask, stated concretely so it is a short email rather than an open-ended one:** the population table — `pop_id`, population name, country, geographic region, ethnic origin, latitude, longitude, `Urban/Rural`, `Family`, `Source`, sample size — for the populations AFND already renders publicly, as one file, with terms permitting us to derive and publish frequency *surfaces* with attribution. We do not need the genotype-level data, and asking only for the metadata we can already read one page at a time is a much easier request for them to say yes to. Contact: support@allelefrequencies.net. Cite Gonzalez-Galarza *et al.* 2020, [doi:10.1093/nar/gkz1029](https://doi.org/10.1093/nar/gkz1029).

`needs-human-decision` because a person has to make the approach and accept whatever terms come back.

## 2. Then: the P1 observations adapter

Once the corpus exists, `genomeos/observations/sources/afnd.py` turns AFND's HLA/KIR/MIC/cytokine allele frequencies into `OBSERVATIONS_SCHEMA` rows joined to the registry entries #18 produces.

**It must consume `registry.sources.afnd.SAMPLING_DESIGN_BY_SOURCE` rather than inventing a design.** That table is already reviewed and tested against `observations.schema.SAMPLING_DESIGNS`; it maps AFND's `Source:` controlled vocabulary onto `sampling_design` and `disease_ascertainment_excluded`, refuses `Other` and anything outside the vocabulary, and flags donor registries as disease-depleted by donor-eligibility policy. §7.1 gives those fields no default, and this is the single point where AFND's ascertainment is established.

Open questions for that work:

- **`cohort_id`.** Per #26's reasoning, the cohort is the contributing *study*, not the sampling site — otherwise there is one cohort level per observation and `β_cohort` is unidentifiable. AFND records author and publication per population; whether that is a usable study key across the corpus is unknown until we can see it.
- **`variant_id`.** HLA alleles are not chr-pos-ref-alt, and `OBSERVATIONS_SCHEMA.VARIANT_ID_PATTERN` requires GRCh38 coordinates. Representing an HLA allele — or deciding that AFND's value here is the *populations* rather than the frequencies — is a real design question, not a mapping exercise. Worth settling before any ingest code is written.
- **Gold/silver/bronze.** AFND classifies data quality (gold = frequencies sum to 1 ±1.5%, n > 50, two-field resolution). Bronze includes all one-field registry data. Which tiers we accept is a scientific choice with a large effect on the retained count.

Also unknown until the corpus lands, and named in #18's PR as unverified: the real refusal rate, the share of degrees-only coordinates (which drives how often the coordinate-precision floor binds rather than the settlement-class extent), and whether AFND's population pages use short display forms of the `Source:` vocabulary beyond the two observed (`Blood Donor`, `Anthropology Study`), which would currently be refused as `unmappable_ascertainment`.

## Correction to the earlier finding

I reported that "frequency data is session-gated". That is **half right and the wrong half matters.** Tested directly:

| endpoint | status |
|---|---|
| `hla6006a.asp` (frequency **search**) | **public** — returns 501 allele records unauthenticated |
| `kir6002a.asp`, `cyt6001a.asp` | public, same pattern |
| `pop6001c.asp?pop_id=N` (population **detail**) | `Access Denied … not logged in` |

So **allele frequencies are publicly served and paginable; population metadata is not.** The gate sits exactly on the half this issue needs — the coordinates.

## 1. Is there an official bulk route?

No. The [AFND 2020 NAR paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC7145554/) describes no bulk download, FTP or API. It offers per-population CSV export for Short Population Reports and for KIR raw genotypes only, one population at a time.

**There is still no licence.** The CC-BY notice in that paper is the standard NAR *article* licence boilerplate, not a grant covering the database contents. Worth stating explicitly because it is easy to misread as one.

## 2. Has anyone redistributed it in bulk?

**Yes, and it is substantial.** [`slowkow/allelefrequencies`](https://github.com/slowkow/allelefrequencies) publishes `afnd.tsv`:

```
123,502 rows · 1,493 populations · 57 genes · 5.99 MB
columns: group, gene, allele, population, indivs_over_n, alleles_over_2n, n
groups:  hla 111,399 · kir 6,714 · cyt 4,517 · mic 872
```

Note 1,493 populations, more than the 1,324 this issue cites. Related tooling: [HLAfreq](https://github.com/BarinthusBio/HLAfreq) (peer-reviewed, [JOSS](https://joss.theoj.org/papers/10.21105/joss.10122)), [hladownload](https://github.com/ramonamerong/hladownload), and `scrapeAF`. All work by paginating the public search endpoints.

**But none of them carry coordinates.** Every one is a frequency table keyed by a population *name string* — "Argentina Rosario Toba", "Algeria Oran". No latitude, no longitude, no `pop_id`.

## What this changes

- **#18 stays blocked**, and now for a precisely identified reason: the registry needs coordinates and ascertainment, and those live behind the one gated endpoint. No existing redistribution supplies them.
- **A P1 path may be open** that we had written off: 123K frequency rows across 1,493 populations, obtainable today. It would need those names joined to coordinates from elsewhere, and that join is exactly the failure mode `geo/countries.py` was built to avoid — a name that fails to match drops a population silently.
- **The ask to AFND should narrow.** Not "the corpus" — just **the population metadata table with coordinates**. It is the part not otherwise available, it is small, and asking only for what we cannot get any other way is a far easier request to grant.

The licence question is unchanged and still governs whether anything derived can be redistributed (#66).

## What the page actually serves, anonymously

With nothing but the ASP session cookie any first visit sets:

```
Geographic Region:  South and Central America
Latitude:   6º 25' S   fctFindLocation2('6','25','S','76','32','W')
Longitude:  76º 32' W
```

The sexagesimal display is duplicated as clean arguments to a JS helper, so it parses without touching the rendered text. Verified across several populations:

| pop_id | lat | lon |
|---|---|---|
| 1986 | −6.417 | −76.533 |
| 2800 | −8.917 | 143.167 |
| 1500 | **8.000** | **77.000** |

That third row is the degree-precision case the merged adapter (#118) already handles: `8º 0' N` has trailing zeros that are **not** significant figures, so it earns a coordinate-precision floor of roughly 78 km rather than being trusted to the arcminute. The adapter was designed correctly for a format we had not yet confirmed was reachable.

## What this changes, and what it does not

**Changes:** #18 is **not blocked on access**. The registry's missing half — coordinates, geographic region, and the `Source:`/`Family:` fields the adapter reads for ascertainment — is publicly readable, one page per population.

**Does not change:** there is still **no licence**. That is now the sole blocker, and it is a decision rather than an obstacle: AFND publishes no terms, so redistributing anything derived from a systematic collection of these pages is a judgement call for the project, not something to assume. #66 governs the same question for other panels.

## Revised ask

The request to AFND is now narrower and more honest: not "please give us access", which we appear to have, but **"please state the terms under which the population metadata may be reused and redistributed."** That is a question they can answer in one sentence, and it is the only thing standing between the adapter and a real run.

## The actual access path

**Hop 1 — `pop6001b.asp`** (public, 1.29 MB, no query needed) lists every population as a link:

```
pop6001c.asp?pop_name=Albania
pop6001c.asp?pop_name=Georgia Caucasus Tbilisi
...  1,825 distinct names from a single request
```

It also accepts `?pop_geog_region=Europe&pop_polyreg=HLA` to slice by region.

**Hop 2 — `pop6001c.asp?pop_name=<name>`** (public with the ASP session cookie any first visit sets) carries the coordinates, duplicated as parseable JS arguments:

```
Geographic Region:  Western Asia
Latitude:  41º 42' N    fctFindLocation2('41','42','N','44','48','E')
```

Verified against known geography:

| population | lat | lon | region |
|---|---|---|---|
| Georgia Caucasus Tbilisi | 41.700 | 44.800 | Western Asia |
| Albania | 41.000 | 20.000 | Europe |
| Greece North Cytokine | 40.000 | 22.000 | Europe |
| Papua New Guinea Madang | −5.217 | 145.800 | Oceania |

**1,825 populations** — more than the 1,324 this issue assumed, and more than the 1,493 in the existing redistribution.

Note rows 2 and 3: whole degrees. That is exactly the case the merged adapter (#118) already handles by refusing to read trailing zeros as significant figures, so `41º 0' N` earns a ~78 km precision floor instead of an arcminute fix.

## Consequences

- **#18 is not blocked on access, and never was.** The adapter can run against the live source, keyed on the same population names the existing frequency redistribution uses — so frequencies and coordinates join on a shared key with no fuzzy matching.
- **`pop_name` is the natural join key**, which also removes the `pop_id` enumeration problem entirely.
- The existing redistribution discarded the very links that make this work; its 1,493 names are one hop from their coordinates.

## The one real blocker

**AFND publishes no licence.** That is now the sole open question and it is a decision, not an obstacle. Collecting ~1,800 population records and redistributing anything derived from them needs terms we do not have, so this stays `needs-human-decision`.

The ask narrows to one sentence: **"Under what terms may the population metadata be reused and redistributed?"** Not a request for access — evidently we have that — and answerable without them building anything.
