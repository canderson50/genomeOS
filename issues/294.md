## Body

## TL;DR

We publish data from gnomAD and dbSNP, but nobody has ever written down, with a date and a link,
whether those sources allow commercial use. Almost certainly they do. The point is that "almost
certainly" is not a record, and a future commercial component would have no way to tell the
difference between "we checked and it was fine" and "we never looked."

Both are currently marked `not_checked`, which is honest but unresolved. This issue is to resolve
them.

---

## What to do

For each source, read the terms, then fill in the `commercial_use` block in
`website/src/atlas/public-artifacts.json` with a `finding`, the date you read them, the https URL
you read, and where the reasoning lives. `docs/non-commercial-data.md` has the field list.

| Source | Current state | Starting point |
|---|---|---|
| gnomAD | `not_checked` | #3 records it as CC0 and links https://gnomad.broadinstitute.org/policies |
| dbSNP | `not_checked` | no record in this repository |

## Why they were not just filled in

gnomAD's terms are described in #3, but without a date, and I am not in a position to be the
verifier of a licence check I would be transcribing from memory — the publication-evidence
safeguards in `AGENTS.md` are explicit that an unperformed check stays `not_checked` and that a
reuse check is never invented. Recording `explicitly_open` with a date I made up would have been
worse than leaving the gap visible.

Verify with:

```bash
python scripts/check_commercial_use.py --list
```

They currently appear under "Sources whose commercial terms have never been checked." When this is
done, that section should be empty.

## Not a blocker

Nothing is broken and nothing is unpublishable because of this. The build accepts `not_checked` on
purpose. This is due diligence that should be recorded before anyone builds a commercial component,
not before the next data PR.

## TL;DR

Merged as `bc420628`. Two things still want a human eye, and merging does not settle them — this is
the `wants-expert-review` pattern, where an agent does the work and a domain expert checks it
afterwards. Recording them here so they do not vanish with the closed issue.

Neither is blocking. Both terms pages are quoted verbatim in
`docs/audits/gnomad-dbsnp-commercial-use.md`, so either can be checked in about a minute without
revisiting the sites.

---

**1. Is `no_restriction_found` the right call for dbSNP?**

NCBI says it "places no restrictions on the use or distribution of the data" and strengthens that by
refusing submissions that arrive with restrictions attached. It then says it "cannot provide comment
or unrestricted permission", because submitters may hold rights and NCBI has none to transfer.

I read that as a completed check that found no restriction, which is what `no_restriction_found`
means here — not an explicit grant. If anything the risk runs the other way: someone might argue
this is weaker than `no_restriction_found`, given NCBI's explicit refusal to grant permission. The
payload is identifiers and coordinates, the least likely category to attract a submitter's claim,
which is why I did not go weaker.

**2. Does gnomAD's public-domain dedication cover what we actually publish?**

The terms place the dedication on "the primary data from the gnomAD exomes and genomes". We publish
aggregated frequency fields derived from that. I read the phrase as covering them rather than only
the raw callset. That reading is the whole basis for the `explicitly_open` finding.

**If either call is wrong**, the fix is to change the `finding` in the declaration and re-run the
gate. Nothing has to be removed from the published data in either case, because neither source
carries a non-commercial restriction on what we publish — the question is only which of two
non-blocking findings is the accurate one.

**A third thing, not a judgement call but worth confirming.** gnomAD's rendered policy page is a
JavaScript application that returns no text to a fetcher, so the quote comes from the markdown file
in `broadinstitute/gnomad-browser` that the page renders. Someone opening the page in a browser can
confirm the two match.
