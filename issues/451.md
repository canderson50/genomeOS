## Body

## Problem

Moving the observation heights rewrites every HbS sampling ring separately. `ObservationLayer.placeAll` re-places all 1,071 rings one `Polyline` at a time. On the next render, Cesium's `PolylineCollection.update` writes their 14.8 MB position buffer as 1,071 separate `bufferSubData` calls of 13,824 B.

While investigating #443 (PR #450), traces showed what that burst can do. On ANGLE Metal (Apple M3 Pro, Chrome 155) it can stall the GPU process for 650–850 ms, and no frame starts until it drains. PR #450 removes the redundant rewrite at the cold commit, which had identical heights. Two paths still change the heights for real and still rewrite every ring:

- **The elevation slider.** It is throttled to 50 ms, so dragging can queue several bursts.
- **A metric switch that shares observations,** which gives new surface heights under the same rings.

Both can hit the same stall in the middle of an interaction, which shows up as a frozen globe for most of a second.

## Proposal

Write the ring positions in one upload instead of 1,071. Possible routes:
- rebuild the rings' collection in one go;
- keep the rings in a single primitive whose vertex buffer is written once per height change;
- move the height to the vertex shader, as a per-instance height attribute plus the elevation factor as a uniform, so a height change uploads a small attribute instead of positions.

## Acceptance

- A cold-load-style probe (or a new interaction probe) shows no long animation frame above the desktop budget (200 ms) while the elevation slider is dragged and while metrics that share observations are switched. Check desktop and the 4× CPU phone profiles.
- A unit test pins that one height change produces one upload, or a bounded number, rather than one per ring.
- Rings stay visually identical. Elevation on and off, and exaggeration, behave as today.

Found during the #443 investigation; root-cause write-up in PR #450.
