## Body

## Summary
Add the AlphaGenome Variant Impact (AVI) score as one more external reference inside the existing per-variant info panel (the slot where #171/#173 added gnomAD, alongside ClinVar and dbSNP). Predicted only, labeled, version pinned. Never mixed with measured data. This is a proposal for triage, happy to close if it is not a fit.

## Why it fits the project
1. genomeOS separates measured observations from inferred/modeled values. AVI is a prediction, so it belongs in the contextual annotation layer (same class as the ClinVar significance notes), never in an evidence surface.
2. The info-panel architecture already exists (#171/#173). This is a data-source addition, not new UI.
3. For the variants genomeOS maps (HbS rs334 first), measured frequency and predicted impact answer different questions and belong side by side but visibly separate: one says how common the change is in each place, the other says how disruptive the change is predicted to be.

## Evidence from a test run (2026-09-09, Antigravity Science plugin: alphagenome + clinvar skills)
- rs334 (chr11:5227002 T>A): AVI Phred 11.77, top 6.65% genome-wide, dominant modality AlphaMissense. ClinVar Pathogenic (2 stars). Measured frequency in this atlas: roughly 0.08-17.3% by region. Three layers, one variant, each correctly labeled.
- HBB intron 2 saturation scan (2,547 SNVs, chr11:5225727-5226575): 64 SNVs score Phred >= 15 (top ~3%); 42 of those have no ClinVar classification (38 absent, 4 VUS). The strongest unrecorded one (c.316-2A>T, Phred 40.50) sits at the same acceptor base where c.316-2A>G is a recorded disease variant (ClinVar 21191).
- Read: the predicted layer is most useful exactly where the clinical record is thin. It points at candidates without pretending to classify them.

## Proposed scope (if accepted)
- One external source card in the variant info panel: AVI Phred, genome-wide percentile, dominant modality, deep link to the AlphaGenome Atlas variant page.
- Labeled Predicted impact (AlphaGenome, model version pinned, access date), separate from Measured and from Clinical significance.
- Server-side cache with model version + date in provenance.
- No use of AVI in source eligibility, curation, or any serving-path science. Predictions never qualify or disqualify a measured source.

## Open questions
1. Terms: AlphaGenome free API is non-commercial; commercial use routes through Google Cloud. Does the project want to depend on that, or show the Atlas deep link only without storing scores?
2. Model version pinning and refresh cadence (Google will recompute predictions over time).
3. Panel hierarchy placement is UI (Brian/Craig to decide).

## Not proposed
No atlas-layer changes, no new map surface, no change to any evidence contract, no AVI in eligibility. Contextual annotation only.

## TL;DR

Two of the licensing worries recorded on this issue are now resolved, and the third has changed
shape. Nothing here blocks the AVI panel any more.

---

**AlphaMissense is not a restriction.** Its predictions moved to CC BY 4.0 in March 2024 (commit
`fe2dc845`, "Update AlphaMissense predictions database license"). The AlphaMissense contribution to
`dominant_modality` imposes no downstream term. The concern recorded earlier on this issue was
reading a stale licence.

**The AVI Score itself is explicitly carved out for commercial use** by DeepMind's own terms, quoted
verbatim in `docs/audits/alphagenome-avi-licensing.md`. That is the part the panel actually renders,
and it shipped in #207.

**The feature breakdown is non-commercial, and that is no longer a veto.** The maintainer has ruled
that non-commercial data may be published here provided it is marked clearly enough to be extracted
wholesale if a commercial component ever exists. #295 builds that: a per-resource declaration naming
the restricted fields, a tripwire that refuses restricted data only when it is *unmarked*, and
`python scripts/check_commercial_use.py --list` as the extraction plan. Rules in
`docs/non-commercial-data.md`.

**What is still open** is #246 — whether the AVI value should come from the permissive bulk download
rather than a read of the Atlas interface, and how often it refreshes. That is an acquisition
question, not a licensing one, and it is the thing to settle before the payload grows.
