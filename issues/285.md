## Reproduction

Run `.venv/bin/python -m pytest` on the local environment reported by `scripts/env_report.py`: Python 3.12.14, PyMC 6.3.1, PyTensor 3.3.0, NumPy 2.5.2. The installed Numba dispatch references `np.row_stack`.

## Actual

`AttributeError: module 'numpy' has no attribute 'row_stack'` during scientific fitting tests. Full run: 17 failed, 558 passed, 12 errors. Retried outside the filesystem sandbox to distinguish compiler-cache permission errors; the NumPy failure remains. No scientific fitting code was changed in the trait-evidence branch (#282).

## Expected

The locked/declared scientific environment can execute its existing validation tests. Do not patch NumPy at runtime, weaken scientific tests, or switch fitting methods to hide this failure. Resolve the dependency compatibility explicitly and regenerate the lock under the repository rules.

The same failure was recorded in the earlier map PR #148. Search of open and closed issues for row_stack / NumPy Numba found no dedicated issue.

### bschilder, 2026-09-16T00:03:44Z (https://github.com/genomeOS/genomeOS/issues/285#issuecomment-5689865275)

## TL;DR

This is closed, but the record should say what actually fixed it. The NumPy version cap that closed
this issue is a safety net, not the cure. The real fix came from Numba, upstream, and would have
arrived on its own.

---

Reviewing #292 before merge, an independent check diffed Numba's released source distributions:

- **0.66.0** — `if numpy_version >= (2, 0): overload(np.row_stack)(impl_np_vstack)`. Unconditional,
  so it reaches the alias NumPy 2.5 removed. This is the crash recorded here.
- **0.67.0** — `if numpy_version >= (2, 0) and numpy_version < (2, 5):`, with the comment *"Numpy 2.5
  removed np.row_stack, so only test it if it's present."* Numba added the guard itself.

Both the capped and the uncapped dependency resolutions select `numba==0.67.0`, so that fix reaches
us from routine lock regeneration whether or not the `numpy<2.5` bound exists. It is also why #292's
own validation could not reproduce the failure against a current resolution — that was not a fluke,
and not something NumPy changed.

NumPy's 2.5.0 release notes confirm the `row_stack` removal is permanent, removed in favour of
`vstack` and deprecated since 2.0. It does not return in 2.5.1 through 2.5.3.

**Why the bound stays anyway.** It costs nothing, NumPy 2.4.6 has no known problems for us, and it
matches this repository's existing practice of putting an upper bound on any library that has
already made two contributors disagree about what the code does while both were right about their
own environment. Treat it as belt and braces rather than as the thing that fixed this.
