## Body

## TL;DR

The public data-store bucket (#468) has no cap on what it can cost, and routine uploads still run as the project owner. The owner decided two controls:

1. **A budget kill switch.** If this month's spend reaches 150% of the project's $200 monthly budget, a Cloud Run function automatically removes public access from the data-store bucket (`genomeos-atlas-data`) until the owner turns it back on. The Atlas web-data bucket keeps serving and is never touched.
2. **An upload-only publisher identity.** A service account that can create new objects in the data-store bucket and nothing else (no overwrite, no delete, no admin). Routine publishing impersonates it, so the owner login can later be retired from agent worktrees.

## Scope

- `deploy/budget-kill-switch/`: a Pub/Sub-triggered Cloud Run function (2nd gen). It parses `costAmount` and `budgetAmount` from each budget notification instead of trusting `alertThresholdExceeded`. At `costAmount >= 1.5 * budgetAmount` it removes every `allUsers` and `allAuthenticatedUsers` member from the target bucket's IAM policy. It is idempotent, writes structured logs, never touches objects, refuses the web bucket, and logs and ignores malformed messages.
- A dedicated runtime identity with a custom role holding only `storage.buckets.get`, `storage.buckets.getIamPolicy` and `storage.buckets.setIamPolicy`, bound on the data-store bucket only.
- A Pub/Sub topic for budget notifications, attached to the existing budget. Its email thresholds and default recipients stay as they are.
- `scripts/provision_budget_kill_switch.py` and `scripts/provision_data_store_publisher.py`: idempotent, with a dry run, and tested against `tests/fake_gcloud.py`.
- `docs/cost-controls.md`: the budget, who gets its emails, what the switch does, how to re-enable public access, how to test the switch, and the weekly spend-email option. Also the publishing runbook in `docs/data-store.md`, moved onto the impersonated publisher.
- A live drill on a throwaway bucket. Nothing in the production bucket is created or overwritten.

Implemented in #481, which is stacked on #474. **Nothing is deployed yet.** This session's permission policy blocked the IAM changes. The dry run is in the PR.

Two things are left for the owner:

1. **Approve one addition to the publisher's access.** `roles/storage.objectCreator` alone cannot upload with `gcloud storage cp`. Before each upload to a new key, cp lists the key as a prefix, and that listing needs `storage.objects.list`. This was traced with `--log-http`; the PR has the details. The PR therefore gives the publisher a custom role, `dataStoreReader`, with exactly `storage.objects.get` and `storage.objects.list`. The `get` means publishing still works after the kill switch removes the public grant; the data it reads is published for everyone anyway. It still has no delete, no overwrite and no admin. The alternative is to keep objectCreator only and stop using `gcloud storage cp` for uploads.
2. **Run the provisioning and the drill.** The commands are in the PR and in `docs/cost-controls.md`.

*Updated 2026-10-17 after review: the role was `dataStoreLister` (list only); it is now `dataStoreReader` (get and list). The PR also lists project-wide access for the owner to decide on: the default compute account holds `roles/editor`.*
