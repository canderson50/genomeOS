## Body

## TL;DR

We built a lookup table so that variants named in an old style (like "IL-6 minus 174") can be connected to their modern genome coordinates. The table works, but nothing actually uses the coordinate it looks up yet — a separate check still rejects the variant for the old reason. So even once someone approves those entries, the four affected variants still will not display their extra annotation, and there will be no error message explaining why. This is the missing second half.

---

## What

The variant-normalization registry landed with `normalized_identity()` used **only** as an `is None` gate. Its `normalized_variant_id`, `rsid` and `strand` are discarded. Meanwhile `scripts/export_atlas_web.py` still enforces:

```python
if normalized != variant_id:
    raise ValueError(...)
```

and its TypeScript twin at `website/src/atlas/contracts.ts:174-184` enforces the same equality.

**Consequence, and it is the one that matters:** when #242 resolves and a cytokine row is flipped to `verified`, that locus **still cannot carry a gnomAD or dbSNP resource.** Declaring `chr7-22727026-C-G` trips the equality check, because the artifact's `variant_id` is `cyt:il-6-174-c`. Declaring `cyt:il-6-174-c` is not a coordinate gnomAD can be keyed by. Both doors are shut.

## Why this is filed rather than fixed

It was found by the final whole-branch review of `feat/variant-normalization-registry`, after the work was scoped. The registry branch's stated scope (design §2, "Included") is the lookup plus the refusal gate — and it delivers exactly that. But design §1's objective and §4's data flow both describe a variant being *usable* under its normalized identity, which this does not yet achieve for mapping rows.

The failure mode if it stays unfiled is quiet: #242 resolves, someone marks the rows verified, nothing appears in the Atlas, and there is no error message pointing at the cause.

## What needs to change

The equality check has to become "the declared `normalized_variant_id` equals **either** the artifact's `variant_id` **or** its reviewed normalized identity from the registry." Both sides:

- `scripts/export_atlas_web.py` — the `normalized != variant_id` check
- `website/src/atlas/contracts.ts:174-184` — `resource.normalized_variant_id !== value.variant_id`

Keep them in step; they disagreeing is what caused the original defect the registry was built to fix.

## Acceptance evidence

- A `verified` mapping row lets its artifact declare a coordinate-keyed resource under the normalized coordinate, and the browser accepts the published catalogue.
- An unverified or absent row still refuses, with the existing message.
- The identity path (HbS) is unchanged.
- A test exercises the mapping path end to end — today `test_every_declared_external_resource_resolves_against_the_real_registry` only exercises the identity path, because no published artifact declares a resource against a mapping row.

## Depends on

#242 — until the verification policy is settled no mapping row can be `verified`, so this cannot be demonstrated end to end. Worth building behind that rather than before it.

Documented in `docs/audits/variant-normalization-2026-09.md` under "A boundary this branch gates but does not yet close".
