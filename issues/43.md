**On GPU acceleration for the raster→H3 step** (context: #104).

The global WorldPop 1 km mosaic is ~933M pixels, and `aggregate_raster_to_h3` does a Python-level `h3.latlng_to_cell` per populated pixel. That loop is the bottleneck at global scale.

Worth being precise about what helps, since [cuSpatial](https://docs.rapids.ai/api/cuspatial/stable/) is the obvious suggestion and is **not** the right tool here:

- **cuSpatial does not implement H3.** It covers quadtree spatial joins, point-in-polygon, haversine and windowing — none of which is the per-pixel indexing we actually do.
- **The real easy win is [`h3ronpy`](https://pypi.org/project/h3ronpy/)** (0.22.0) — a Rust/Arrow H3 implementation with a vectorised numpy API. It replaces the per-pixel Python call with an array call, on CPU, with no CUDA dependency and no accuracy change.

That ordering matters for contributors: a CUDA-only dependency in the offline pipeline is a real cost to anyone without an NVIDIA GPU, and it would buy us nothing on the step that is actually slow.

Where cuSpatial *does* earn its place is #94's country assignment — `quadtree_point_in_polygon` over millions of H3 cells against GADM polygons.

Not blocking this issue as merged; the current implementation is correct and windowed, and the tests run against small synthetic rasters by design. This is a note for whoever first runs it on the full 870 MB mosaic and finds it slow.
