## Body

## Problem

Against the public web data bucket (#406, PR #437), the first page load in a freshly launched Chrome takes about 3 s longer than later loads. Later loads, and every median, match the old same-origin numbers.

- **Formal §B.1 cold-load harness**, headed Chrome 154 on an M3 Pro with a hardware GPU: desktop run 0's `observations-visible` was 3,363 ms (I2) and 3,327 ms (I3). Runs 1–2 were 378–392 ms.
- **Local control:** the same staged tree served cross-origin from `127.0.0.1:4323` (CORS + gzip) adds only about 130 ms to run 0: 542 ms against 374–413 ms.
- **Phone profiles** reuse the already-running browser and show no run-0 penalty.
- **Network probe:** a direct probe of the bucket from a freshly launched Chrome took about 0.2 s end to end: DNS 15 ms, connect about 50 ms, TLS about 30 ms, TTFB 20–70 ms. Connection setup alone doesn't explain 3 s.

## What to find out

Is this an artefact of a fresh automated profile, such as Chrome's first-run traffic to Google hosts competing for the connection pool or the main thread? Or would a real first visit to genome-os.org see it too?

## Suggested approach

1. Record a DevTools performance trace and a NetLog (`--log-net-log`) of a fresh-profile first load against the production build. Compare it with run 1 and with the local cross-origin control.
2. Check whether the `preconnect` to the data origin is used, and what else is on the wire in the first 3 s.
3. If a real first visit is affected, fix it (for example, preconnect timing or an earlier critical fetch) and add a run-0 check to the harness.

## Acceptance

- The cause is named, with trace evidence.
- If it affects real users, the first fresh-profile load is within about 0.5 s of later loads.
