## Body

The default HbS map takes 9.6–12.9 s to load on desktop and 33 s on mobile (4× CPU, Fast 4G). On Slow 4G it never loads, because the 15 s request timeout fires. Profiling shows most of the time is main-thread geometry:
- a single 12.8 s `setArtifact` task;
- a 6.9 s outline build;
- 4.0 s of synchronous Cesium combine;
- 8.8 s downloading 20 MB of JSON.

**Scope:** Part B of the design spec `docs/superpowers/specs/2026-10-07-atlas-mobile-fast-load-gcs-design.md` (§B.1–B.9):
- GOSA v1 grid/render/detail tiers, encoded offline with a stdlib-plus-h3 codec and generated in CI;
- an inline catalog and URL-aware preloads;
- one Cesium-free worker that verifies (sha256), decodes and validates the data, then builds the chunked mesh, the support mask, the edges and the Natural Earth context;
- an atomic swap for every replacement of a displayed layer;
- artifact-keyed picking;
- lazy Cesium;
- the cold-load harness with explicit CDP profiles.

**Acceptance (median of 3, hardware GPU):**

| Profile | Observations visible | Surface visible |
| --- | --- | --- |
| Desktop | ≤ 1.5 s | ≤ 2.5 s |
| Mobile, Fast 4G | ≤ 4 s | ≤ 6 s |
| Mobile, Slow 4G | ≤ 13 s | ≤ 18 s |

- No Atlas long animation frame over 200 ms on desktop or 800 ms on mobile.
- Same-input visual parity, as defined in the spec.
- Every displayed number comes from the f64 detail tier.

**Not in scope:** a coarse aggregated preview. It needs a human decision on masked-cell aggregation (AGENTS).

Related: #172.

## Measured: old vs new load time (informal, local, 3 cold loads per cell)

The build after the Part B switch-over (Task 69), compared with the current site code. Both were served from the same machine under the same throttling.

| Profile | Old build: map ready | **New: points visible** | **New: map ready** | Time saved to a usable map |
| --- | --- | --- | --- | --- |
| Desktop, no throttling | **8.8 s** (8.7–9.2) | **0.4 s** (0.4–0.4) | **1.3 s** (1.3–1.4) | **7.5 s** (~6.8× faster) |
| Phone, 4× slower CPU, Fast 4G | **33.0 s** (33.0–33.1) | **3.2 s** (3.2–3.4) | **4.3 s** (4.2–4.4) | **28.7 s** (~7.7× faster) |
| Phone, 4× slower CPU, Slow 4G | **never** (3/3 runs gave up at 150 s) | **13.3 s** (13.3–13.3) | **14.2 s** (14.2–14.3) | from never to 14.2 s |

Values are medians, with the range of the 3 runs in parentheses. The old build shows observation points and the surface together; the new one shows points first.

**Against the spec §B.1 budgets.** These are informal numbers. The formal gate is the cold-load harness in Tasks 83–84.
- Desktop: ≤ 1.5 s / ≤ 2.5 s. Met: 0.4 s / 1.3 s.
- Fast 4G: ≤ 4 s / ≤ 6 s. Met: 3.2 s / 4.3 s.
- Slow 4G: ≤ 13 s / ≤ 18 s. The map meets its budget at 14.2 s. Points are borderline at 13.3 s.

### Method
- **Builds.**
  - Old: the Part A site code that is on `main` now (#408, `d09390b` tree), loading the 20 MB JSON surface.
  - New: `feat/atlas-fast-load` at `789b17e`. This is a local branch, 39 of 52 Part B tasks complete, and it will be the Part B PR. It loads GOSA binary tiers, encoded from the same committed export by `scripts/encode_atlas_web.py`.
- **Serving.** Both builds were served by `serve` from the same Mac, Apple-silicon desktop class. The new one uses the `.gosa` gzip rule.
- **Browser.** Headed Chrome with a hardware GPU, a fresh browser context and the HTTP cache disabled for every run.
- **Throttling.** CDP `Emulation.setCPUThrottlingRate` at 4 and `Network.emulateNetworkConditions` with the DevTools presets:
  - Fast 4G: 165 ms latency, 1,012,500 B/s down.
  - Slow 4G: 562.5 ms latency, 180,000 B/s down.
- **Phone profile.** 390×844 at DPR 3, mobile and touch.
- **Timing.** Polls the `.atlas-explorer` readiness attributes from navigation start:
  - `data-atlas-observations-visible` for points;
  - `data-atlas-ready` for the full map: surface, mask and observations.

### Caveats
- **The new background worker is not CPU-throttled here.** CDP throttles only the page. The decode, verification and mesh build that run in the worker go at full desktop speed, so the phone rows favour the new build somewhat. The formal harness (spec §B.1) throttles worker targets too, or scales the worker steps ×4, and reports the median of 3 against the budgets.
- **Network.** The network is simulated, so there is no real CDN latency. Real-world numbers on genome-os.org will also reflect Part C (#406), which serves the data from GCS with immutable caching.
- **Why serving locally doesn't explain the gain.** Served locally with no throttling, the old build still takes 8.8 s on desktop. The old load was dominated by main-thread geometry work, not download (see the profile in the design spec §0).

The formal numbers, and before/after figures, will be in the Part B PR.

## Day/night shading is not a speed lever, measured

I checked whether turning off day/night globe shading (`?dayNight=false`, i.e. `globe.enableLighting`) would speed things up further. Same build (`789b17e`), same method as the comment above, 3 cold loads per cell:

| | Shading on (default) | Shading off |
| --- | --- | --- |
| Desktop, map ready | 1.23 s (1.20–1.36) | 1.24 s (1.18–1.33) |
| Phone, 4× CPU, Fast 4G, map ready | 4.17 s (4.15–4.18) | 4.27 s (4.17–4.43) |
| Desktop, dragging the globe for 4 s | ~105 fps, p95 frame 16.6 ms | ~96 fps, p95 frame 16.7 ms |

The differences are within run-to-run noise. Shading adds one per-pixel lighting term to the globe shader; it does not touch the download, decode or geometry work that the load time is made of.

**Decision: keep shading on by default.** One limit on this: the drag test ran on an Apple-silicon GPU. A low-end phone GPU pays relatively more per pixel, but even there shading affects frame rate after the map has loaded, not load time.
