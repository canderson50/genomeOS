## Body

## What

`LITERATURE_SEARCH_COLUMNS` has no field for **who made a screening decision**:

```python
LITERATURE_SEARCH_COLUMNS = (
    "search_id", "corpus_id", "database", "query", "executed_at", "candidate_id",
    "decision", "decision_reason", "manifest_version",
)
```

So an `included`/`excluded` verdict carries a reason but no origin. There is no way to tell a human screen from an agent screen, and no way to tell whether the screener was the same party as the extractor.

## Why this is inconsistent with the rest of the ledger

The evidence ledger is careful about exactly this. `LITERATURE_EVIDENCE_COLUMNS` separates `extracted_by` from `verified_by`, `extraction_method` distinguishes `manual_transcription` from `automated_proposal`, and the curation contract requires the two identities to differ, because "self-review cannot catch a shared transcription or interpretation error."

Screening gets none of that, yet it is a judgement call with real consequences: an `excluded` verdict removes a paper from the corpus, and nothing downstream revisits it. A wrongly excluded population measurement is invisible — it leaves no refusal, no unresolved state, and no coverage-report row. It is the one decision in this pipeline that fails silently.

## Concretely, from #188

Screening in that PR is authored data with no derivable origin, which is correct — a screening judgement is not something code should reproduce. But its extraction is `agent:hermes-sentinel:4.0`, and the manifest cannot record whether the same agent also made the 13 exclusion decisions. `PROVENANCE.json` records the screening `manifest_version` and the snapshot it revises, which is good, but not by whom:

```json
"screening": { "manifest_version": "...@2026-09-09.2", "over": "...@2026-09-09.1" }
```

This is not a defect in #188 — the contributor recorded everything the schema allows. The schema is what is missing a column.

## Suggested change

Add `screened_by` to the search manifest, in the same format `extracted_by` already uses (`human:<slug>`, `agent:<provider>:<model>`, `import:<name>@<40-hex>`):

- Required on any row whose `decision` is not `pending`; blank on `pending`, since a discovery snapshot has no screener by construction.
- The existing `fetch_pubmed_manifest.py` needs no change — it only ever emits `pending`.
- Consider whether an agent screen should additionally require independent confirmation before a corpus is promoted, mirroring the extractor/verifier split. That is a policy question rather than a schema one, and worth deciding separately from the column.

Whether to also record it per manifest version rather than per row is worth a moment's thought: a version is screened in one pass by one party, so a version-level record is less repetitive, but a per-row column matches how the rest of the ledger works and survives a partial re-screen.

## Acceptance evidence

- A non-`pending` row without a valid `screened_by` fails validation.
- A `pending` row with a `screened_by` fails validation too — the state and the identity have to agree.
- Existing fixtures migrate, and the frozen `contract/` diff is committed.
- The curation doc's manifest column table gains the row, with a prohibited-shortcut example.

Since this changes a schema, it needs `python scripts/freeze_contract.py` and a committed contract diff.

Design sections: §5.1 (`literature_searches`), §5.2.5 (extraction and independent verification, for the format to mirror).

## Not implementing this yet: the column's shape depends on a policy decision, and the backfill would require inventing data

Two problems surfaced when I went to build it. Both are reasons to decide before coding, not reasons to drop it.

### 1. The schema shape depends on the unanswered policy question

My original write-up buried this as an aside. It is actually the deciding factor. If an agent screen must be independently confirmed before a corpus promotes — mirroring the `extracted_by` / `verified_by` split the evidence ledger already enforces — then the manifest needs **two** columns, not one, and validation has to enforce that they differ. If it does not, one column suffices.

Building `screened_by` alone and adding a confirmation column later means a second contract change and a second fixture migration over the same files. Worth answering first.

The substantive question: **is a screening exclusion a claim that needs independent review, or a curation judgement that stands on its reason alone?** The argument for review is that a wrong exclusion is the only decision in this pipeline that fails silently — it leaves no refusal, no unresolved state, and no coverage row, so nothing downstream can detect it. The argument against is that every exclusion already carries a written reason, which is auditable by inspection in a way a transcription error is not.

I lean toward requiring confirmation for agent screens only, but this is a governance call on the project's behalf, so I am adding `needs-human-decision` rather than picking.

### 2. Backfilling existing rows would mean inventing the very metadata this guards

Three manifests already carry screening decisions: `lct-enattah-2007/searches.tsv` (37 rows) and, from #188, `hbb-rs334-salih-2010/searches.tsv` (44 rows, 13 excluded). **Nothing records who screened any of them.** Writing a plausible `agent:...` value into those rows would be exactly the invented-metadata failure the whole ledger exists to prevent — and it would be worse than the current blank, because a blank is visibly unknown while a fabricated identity reads as verified provenance.

The project's own idiom gives the answer: an explicit unknown state, never a guess or a blank. Something like `not_recorded`, sitting alongside `not_reviewed` and `not_checked`, permitted **only** on rows whose manifest version predates the column and rejected on any new one. That keeps the migration honest and stops the sentinel becoming a permanent escape hatch.

Worth noting `search_id` is unaffected either way — it hashes `(database, query, executed_at)`, not the column set — so adding a column re-mints no identity. That is the one part of this that is genuinely cheap.

### What I would build, once the policy is settled

1. `screened_by` (and `screening_confirmed_by`, if required) in `LITERATURE_SEARCH_COLUMNS`, formatted as `extracted_by` already is.
2. Validation: required on any non-`pending` row, rejected on `pending`, `not_recorded` accepted only for the three pre-existing manifest versions named explicitly.
3. `scripts/fetch_pubmed_manifest.py` needs no change — it only ever emits `pending`.
4. Fixture migration, `freeze_contract.py`, committed `contract/` diff, and the curation doc's manifest column table gains the row with a prohibited-shortcut example.

Leaving this open and labelled for the decision. The rest of the review findings are dealt with: #231 and #234 in #243, #235 in a PR alongside it, and #237 rescoped after its own blocker.

### bschilder, 2026-09-12T00:45:40Z (https://github.com/genomeOS/genomeOS/issues/242#issuecomment-5642274229)

## Decision (@bschilder, 2026-09-11): agent verification is permitted, backed by links a human can check

> "yes it can be agent verified, with links that a human can verify if needed afterwards"

That settles the governance question this issue was blocked on, and it settles it for both places it bites.

**What it means concretely.** A verifier may be `agent:<provider>:<model>`, provided the verification rests on **links a human can follow and check independently**. The audit trail is the point: verification is not an assertion that an agent looked, it is a set of references that make re-checking cheap. An agent verdict with no resolvable links is not verification under this decision.

**The extractor/verifier split still holds.** This permits an agent to be *a* verifier, not to be *its own* verifier. The existing rule that `verified_by` must differ from `extracted_by` is unchanged — what changes is that the differing party may now be another agent rather than only a human.

## Two consequences

**1. This issue's own subject — the `screened_by` column.** The policy question in §1 of my earlier comment is answered, so the schema shape is decided: **one column, not two.** No separate `screening_confirmed_by` is needed, because an agent screen is now a legitimate screen rather than a proposal awaiting human confirmation. What the column must carry is the identity plus, for an agent, resolvable evidence.

The backfill problem is unchanged: nothing records who screened the three existing manifests, so those rows still need an explicit `not_recorded` state rather than a fabricated identity. Still worth doing; still a schema change with a contract diff.

**2. The variant-normalization registry, merged today as #259.** Its four cytokine rows are `verification_status: pending` precisely because of this issue, and they carry exactly the evidence this decision asks for — dbSNP build 157 and Ensembl release 116 placements, the PMIDs that establish each legacy name, and in one case an orientation argument against this repo's own published observations.

Those can now be verified by an **independent** agent — one that did not resolve them — re-checking each link. I am doing that as a separate, attributable act rather than editing the merged rows quietly, since "a distinct verification event" is what makes the split meaningful.

Note this does **not** on its own make those loci usable: #256 is the other half, and until that lands a verified mapping row is still refused by an equality check in the exporter.
