## Body

## Trigger and observed bottleneck

The frozen B0H calibration on pod `uio8ugez2dedzo` exposed a critical-path performance gap in
`scripts/run_b0h_calibration.py`. The `run` command executes every manifest case through one
sequential loop:

```python
for case in manifest.cases:
    ...
    execute_b0h_case(manifest, case, store)
```

At source revision `d98794b18b64e230cbdbae8b23d37488a42de804`, an instantaneous pod snapshot
showed one runner process at about 152% CPU on a 252-vCPU host, 690 threads, 56.8 GiB RSS, and 0%
GPU utilization. The exact SQLite state advanced correctly with zero failures or ownership losses,
but only 1,047 of 1,938 cases were complete after roughly 11.8 hours of process runtime. The GPU
number is a snapshot rather than a utilization trace; sustained profiling is required before
attributing the bottleneck.

Do **not** modify, restart, add a writer to, or otherwise accelerate the current frozen campaign.
Its controller attests that the running command is the sole scientific invocation. This issue is for
fresh future campaigns only.

## Scientific objective and claim

Reduce the wall time and cost of exact B0H calibration without changing any case definition,
random seed, posterior-rank statistic, failure/refusal behavior, completion digest, or reduced
scientific result.

The claim is operational: independent manifest cases can be scheduled concurrently while retaining
the campaign's exactly-once publication and immutable evidence contracts. No predictive or
scientific improvement is claimed.

## Measurable output and acceptance evidence

1. Add sustained CPU/GPU/memory/I/O profiling around a representative serial reference run and the
   proposed concurrent run. Report full-workflow wall time, throughput, peak RSS, worker count, and
   hardware; do not use kernel-only timing.
2. On a deterministic fixture manifest, serial and concurrent executions must produce identical
   case identities, completion/failure classifications, completion digests, inventory digest, and
   reduction bytes. Compare retained evidence by case rather than relying only on a passing exit
   code.
3. Exercise worker interruption, duplicate delivery, pending publication, and resume behavior.
   Every case must remain exactly once in the admitted inventory; ownership loss or ambiguous
   publication must refuse reduction.
4. Demonstrate at least 2x end-to-end speedup on a representative multi-case calibration. Record
   where scaling stops and choose a bounded default from measurements.
5. Measure thread oversubscription. A worker design that multiplies the current JAX/XLA/BLAS thread
   pools without improving end-to-end time fails this issue.
6. Preserve the existing serial mode as the equivalence oracle until the concurrent path passes all
   conformance checks. Do not weaken any calibration, admission, or reduction gate.

## Engineering component and public interface

Implement a deterministic research-side scheduler behind `scripts/run_b0h_calibration.py` and the
existing B0H store contracts. Candidate implementations may use bounded case workers with one
publication coordinator, or isolated shard stores followed by a verified deterministic collection;
choose using measured contention and recovery behavior.

The CLI must expose the chosen bounded concurrency explicitly in the frozen campaign record. Worker
ordering may not affect per-case seeds or artifact identity. Avoid Python case-by-draw or
case-by-sample nested loops in measured paths; use existing batched array operations within a case
and process-level case parallelism only where the retained-memory profile permits it.

This is offline tooling. Serving APIs and published artifact schemas remain unchanged.

## Assumptions, refusals, and downstream consumers

- Cases are independent only after the manifest, null record, source revision, environment, and
  per-case seeds are frozen.
- SQLite multi-writer behavior is not assumed safe merely because a short test passes. Retained
  publication and crash-recovery evidence decides the architecture.
- Refuse mismatched manifests, source/runtime drift, duplicate or missing cases, conflicting
  completion digests, ownership loss, unresolved publication, or non-identical serial/concurrent
  reductions.
- A transient 0% GPU sample does not prove the workload never uses the GPU. Capture a time series.
- The current in-flight B0H v2 run is an immutable reference and is outside this issue's mutation
  scope.

Downstream consumers are repeated B0H calibration, B1G and later candidate calibration, and the
global modeling campaign's model-comparison ladder. This advances the campaign plan but closes none
of its scientific validation gates.

### v3r15 live-profile follow-up

The corrected-profile v3r15 comparison provides a second, more specific measurement while remaining immutable. Three independent A100 SXM 80 GB seed shards are still on their first planned comparison command at source `887c32c3724b97fc1c010c4b716f17039643b2db`. No process was modified, attached to, restarted, or rescheduled.

Five one-second `nvidia-smi dmon` samples per pod were stable:

| Seed | GPU SM utilization | Framebuffer memory | Power | Runner CPU |
|---:|---:|---:|---:|---:|
| 42 | 18% in all 5 samples | 3,213 MiB | 85 W | 99.9% of one core |
| 43 | 19–20% | 3,725 MiB | 96–97 W | 100% of one core |
| 44 | 19% in all 5 samples | 3,709 MiB | 73 W | 100% of one core |

This short synchronized window is stronger than the earlier instantaneous 0% observation, but it is still not the sustained full-workflow trace required by this issue. It shows that the active NumPyro workload does use the GPU while leaving substantial device capacity idle, which keeps bounded case-level concurrency worth testing on a fresh campaign.

I also measured the conspicuous nested post-fit `training_counts` aggregation in `fit_reference_population_heterogeneity` against the exact 510-variant input shape used here: 32,640 available training rows and 510 variants. The existing repeated scans took 0.5634 s; exact `int64` NumPy `bincount`/`add.at` accumulation took 0.000764 s, produced identical `VariantTrainingCounts`, and was 737× faster in this microbenchmark. That loop should eventually be replaced, but its subsecond absolute cost cannot explain the multi-hour end-to-end runtime and is not a reason to mutate or restart v3r15.

The acceptance target should therefore retain full-workflow profiling and bounded case concurrency. Optimizing only the aggregation loop would make the code cleaner without meeting the required 2× end-to-end speedup.

### Result

The calibration runner now uses isolated science workers with one SQLite publication owner, durable checksummed result packets, and restart recovery. A repeated 32-case A100 confirmation measured:

| Workers | Median wall time | Throughput | Speedup | Cost/case |
|---:|---:|---:|---:|---:|
| 1 | 805.2 s | 143.1 cases/hour | 1.000× | $0.01111 |
| 4 | 403.0 s | 285.9 cases/hour | 1.998× | $0.00556 |
| 5 | 401.2 s | 287.6 cases/hour | 2.010× | $0.00554 |

Five workers are therefore the smallest measured configuration that passes the predeclared 2× gate. It is now the calibration default. Explicit `--workers 1` preserves the serial path. Five is the highest measured calibration count because the small throughput gain over four workers increased peak RSS from 8.01 to 9.37 GiB and peak threads from 1,307 to 1,614. Explicit higher counts remain available and are frozen in the campaign record, but are unmeasured.

The heavier reference workload has a separate measured limit. Two workers improved throughput by 1.38× and cut cost per case by 27.5%. At three workers, one repeat completed but another reached 81,142 MiB of the 81,920 MiB GPU and lost a subprocess. Four workers were not launched into that observed ceiling; reference runs remain bounded at two.

### Correctness evidence

- Fixed-clock serial and concurrent runs match exactly on case order, terminal classifications, completion digests, complete inventory digest, and final reduction bytes.
- Tests cover worker loss, draining active results, duplicate delivery, corrupt packets, pending publication, parent restart, and recovered publication.
- Every real benchmark repetition produced the same terminal case/stage classifications.
- Independent NumPyro GPU processes did not yield byte-identical raw posterior arrays, even serially with the same seed and environment. The public report records that boundary explicitly rather than calling the raw bytes equivalent.

The complete note, compact reports, and three review figures are in PR #354 under `docs/research/` and `docs/figures/`. Private posterior and benchmark inputs remain outside Git. The existing v3r15 pods and artifacts were not modified.

Final local validation passed: 43 focused tests; 5,826 full-suite tests with 33 skipped; smoke; Ruff; frozen contract; module-size; staged privacy gate. CI is running on the final commit.
