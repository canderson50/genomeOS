## Body

Three options: (a) containerise R + R-INLA, call from Python with a parquet hand-off — keeps the spec's method and its defensibility to reviewers, adds an R toolchain; (b) sdmTMB/TMB — still R; (c) reimplement in PyMC or GPyTorch — one language, but gives up the 'same lineage as the model-based geostatistics literature' argument that makes §7 defensible.

**Blocks all other P2 work. Decide first.**

### bschilder, 2026-08-23T01:34:37Z (https://github.com/genomeOS/genomeOS/issues/34#issuecomment-5383606335)

**Recommendation: containerised R-INLA, called from Python with a parquet hand-off** (option a).

Reasoning, in the order that actually decided it:

1. **The golden tests are what establish correctness, and they only work if we can be compared.** HbS parity means reproducing Piel et al. 2013. Their lineage *is* model-based geostatistics via INLA-SPDE. Using the same method means a discrepancy is informative — it points at our data or our priors. Using a different method means a discrepancy is ambiguous, and we'd have to debug the model and the pipeline simultaneously.
2. **Marginal posteriors at batch cost.** We need per-cell `post_sd` and `q025`/`q975` for tens of thousands of variants. INLA gives proper marginals without MCMC's per-variant wall-clock. A variational GP gives us a posterior that is *systematically* over-confident, which is the worst possible failure mode for a project whose central honesty mechanism is the uncertainty layer.
3. **The R toolchain cost is bounded and one-directional.** It lives entirely inside the P2 batch container. Nothing on the serving path touches R — spec §5 already guarantees no inference on the read path — so this adds one Dockerfile, not a second language across the codebase.

**Contract:** the container reads observations parquet, writes surfaces parquet keyed by `(variant_id, h3_res, h3_parent)`. Python orchestrates; R only fits. That boundary keeps `surface-fit` a pure function of `(config, data_version, seed)` per §5, so it stays unit-testable from Python without an R dependency in the test suite.

**What would change my mind:** if the SPDE mesh construction turns out to be the bottleneck at our variant count rather than the fit itself, a fixed shared mesh across variants (fit once, reuse) is the fallback — and that is much easier to implement in Python. Worth measuring during golden test 1 calibration rather than deciding up front.

Tagging @dwgoblue — this is the decision I'd most like a second opinion on before it hardens into a Dockerfile.

### bschilder, 2026-08-24T19:58:05Z (https://github.com/genomeOS/genomeOS/issues/34#issuecomment-5400579336)

## Findings, and a recommendation

Researched this. Short version: **there is now a Python INLA, but it should not be our dependency — and once we stop treating INLA-SPDE as the requirement, a better-fitting Python option already exists.**

### pyINLA exists, and has a blocking catch

[pyinla.org](https://pyinla.org/) is a native Python interface to the *same C/C++ INLA computational core* as R-INLA — not an `rpy2` wrapper. SPDE meshes, 50+ likelihoods, disease mapping. On paper it is exactly what §7 asks for and it would close this issue as option (d).

But [on PyPI](https://pypi.org/project/pyinla/):

```
version: 0.1.8   releases: 3   requires-python: >=3.10
license: Proprietary
summary: Python interface for INLA ... with bundled binaries
```

`License: Proprietary`, **with bundled binaries**, at v0.1.8, and the site says it is "in an internal testing phase… expect rapid changes as we harden the API."

For most projects that is wait-and-see. For this one it is close to disqualifying at the core of the pipeline. Our premise is that a cited map can be regenerated at a fixed version years from now (design §5, §13); a closed binary blob in the inference step means contributors cannot rebuild it, and it may collide with whatever licence the repo adopts (#65 is still open). By contrast **R-INLA itself is GPL-2+ with source on GitHub** — the proprietary piece there is only the optional PARDISO solver.

**Action:** worth mailing contact@pyinla.org to ask whether "Proprietary" is intent or a packaging placeholder. If it resolves to something open, this becomes the obvious answer and we should revisit.

### Reframing: what §7 actually requires

Not "INLA-SPDE" but:

1. a binomial-type likelihood with a spatial random field and fixed effects,
2. **proper marginal posteriors** — non-negotiable, since `posterior_contraction` (posterior sd ÷ prior sd) is what drives the `prior_dominated` mask (§7.1b),
3. per-variant cost cheap enough to batch over the curated set,
4. defensibility.

### Recommendation: PyMC + HSGP

[`pymc.gp.HSGP`](https://www.pymc.io/projects/docs/en/stable/api/gp/generated/pymc.gp.HSGP.html) — a Hilbert-space reduced-rank GP approximation whose basis functions do not depend on the covariance hyperparameters, so they are precomputed once and inference scales **linearly rather than cubically**. PyMC's own docs describe it as suited to "a two dimensional spatial point process" with Matérn kernels — this exact shape. Stable, pure Python, full posteriors, and it drops straight into the pure-offline-deterministic-function architecture P2 already assumes (§5).

Behind it, [`pymc-extras`](https://github.com/pymc-devs/pymc-extras) now ships an actual **INLA** implementation (2025 GSoC: Newton solver for the Gaussian mode plus a marginalisation routine), alongside Pathfinder, DADVI and Laplace. Experimental, but the same algorithm in the same ecosystem — a natural cross-check rather than a fork in the road.

**On defensibility:** the plan worried that leaving R-INLA abandons the "same lineage as the model-based geostatistics literature" argument. I think that is overstated, because **§8 already makes our standard of proof empirical rather than genealogical.** If we reproduce Piel et al.'s intervals, the method is validated by parity against published numbers — a stronger claim than "we used the same software."

### The finding that matters more than the engine

A malaria-specific comparison of INLA, GPBoost, spatial random forests and FRK ([Comparison of new computational methods for spatial modelling of malaria](https://pmc.ncbi.nlm.nih.gov/articles/PMC10664662/)) reports that **INLA with a standard binomial response produced "spuriously flat, near-zero predictions on sparse data"**, because prevalence was overdispersed relative to binomial — and that **switching to Beta-binomial resolved it**. FRK oscillated in data-sparse regions; spatial RF produced arc-shaped artifacts.

§7 specifies exactly `AC_i ~ Binomial(AN_i, expit(...))`. So the sharpest documented failure mode in this literature is in the **likelihood, not the engine** — and "spuriously flat near-zero predictions on sparse data" is precisely what the `prior_dominated` mask exists to catch, which is some validation of that design.

Caveat worth stating: that study models infection *prevalence*, overdispersed partly because infection clusters socially. Allele counts may be closer to genuinely binomial, since genotype is fixed per individual. Beta-binomial nests Binomial, so carrying the extra parameter is cheap insurance and the data can decide. Split out as its own issue.

### Proposed decision

- **PyMC + HSGP** as the surface-fitting engine (Matérn-5/2, binomial likelihood, `β_design` / `β_cohort` as fixed effects).
- **`pymc-extras` INLA** as a cross-check once it stabilises.
- **Beta-binomial alongside Binomial**, selected by fit rather than by assumption.
- **Revisit pyINLA** if its licence clears.
- No R toolchain.

Implementing this now in #35. Flagging `wants-expert-review`: the HSGP-vs-SPDE substitution and the `m`/`c` basis-function settings are the parts where a spatial statistician's read would most lower the risk.

### bschilder, 2026-08-24T20:24:55Z (https://github.com/genomeOS/genomeOS/issues/34#issuecomment-5400892475)

**Decided and implemented** in #84 (closed #35).

**PyMC + HSGP.** No R toolchain. `genomeos/surfaces/fit.py` implements §7's model — binomial likelihood over a Matérn spatial field with `β_design` and `β_cohort` offsets — and recovers a known design effect from synthetic data inside its 95% CI.

Recorded for anyone revisiting this:

- **The binding requirement was proper marginal posteriors**, not the INLA algorithm. `posterior_contraction` (§7.1b) is defined as *posterior sd ÷ prior sd*, so an engine without real posteriors cannot support the data-support mask — the honesty guarantee the project rests on. That ruled out the fast point-estimate approximations immediately.
- **pyINLA is the one to watch.** Native Python interface to the same C/C++ INLA core, so it would be a near drop-in. Blocked on PyPI declaring `License: Proprietary` with bundled binaries at v0.1.8. Reopen this if that clears.
- **Defensibility is empirical here**, per §8: parity against Piel et al. is a stronger claim than sharing an implementation lineage.
