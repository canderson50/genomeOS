## Body

## TL;DR

Some of the data we want to use is free for research but not for commercial use. We should be able
to use it — but only if every piece of it is labelled, so that if genomeOS ever grows a commercial
side, one command tells us exactly what has to come out. Right now we have no such labelling, so our
only option has been to refuse non-commercial data outright, which costs us real evidence for no
good reason.

This issue asks for the labelling mechanism. It does not add any restricted data.

---

## Why now

Reviewing #207 I told the contributor to drop AlphaGenome's `top_attributions` field, because
DeepMind defines the AVI Score Feature Breakdown as separate from the AVI Score and licenses it for
non-commercial use only. That was the right call given what the repository could express at the
time: a blanket refusal was the only tool available.

The maintainer's ruling is that non-commercial data **may** be included, on the condition that it is
marked clearly enough in the code and in issues and pull requests that a future commercial component
can extract all of it at once.

## The shape of the problem

The restrictions we actually face are **field-level inside an otherwise-permissive source**, not
source-level:

- DeepMind carves the AlphaGenome AVI Score out for commercial use, but not the Feature Breakdown.
- gnomAD is CC0, but the SpliceAI annotations it bundles are CC BY-NC (already noted in `AGENTS.md`).

So a licence tag attached to a whole source is wrong in both directions. It would either over-claim
the restricted half or condemn the permissive half — and a commercial build wants to drop one
AlphaGenome field while keeping the score it is entitled to use.

## What this needs

1. A per-resource declaration in the publish allowlist naming the finding and the exact restricted
   fields, reusing the reuse-check vocabulary the literature evidence already uses.
2. A tripwire so a field already known to be restricted can ship **marked** but never **unmarked** —
   preserving the protective value of the refusal it replaces.
3. One command that turns the declarations into an extraction list.
4. A CI gate, so a stale export cannot silently drop a restriction from the published data.
5. Conventions for humans: a `NON-COMMERCIAL:` code comment that a plain search finds, a
   `licence:non-commercial` label, and a line in the pull-request template.

## Deliberately not in scope

Re-adding `top_attributions` to any payload. That is a data-acquisition change, and it is gated on
the open acquisition-path question in #246, not on the licence. This issue builds the machinery that
would let it be added and stay findable.

## Design constraint worth stating

`not_checked` must stay publishable. Refusing it would leave a contributor choosing between
abandoning the data and inventing a licence finding to make the build pass, and inventing a reuse
check is exactly what the publication-evidence safeguards forbid. Unchecked sources belong on the
extraction list under their own heading instead — for an extraction, "we never read these terms" is
as actionable as "we know this is restricted".
