## Body

## TL;DR

Our schemas correctly reject a genuinely missing value in a required field. They do **not** reject
the *word* for one.

A cohort identifier of `"NA"`, `"None"`, `"nan"`, `"null"`, `"-"`, `"."` or a single space all pass
validation today as if they were real identities. Nothing in our committed data does this yet, so
this is a gap to close rather than a bug to fix.

Found by sweeping for silent repairs other than the integer truncation fixed in #323 and #339.

---

## What was swept, and what came back clean

Every column of every coercing schema was handed values that could plausibly be repaired into
something valid. Most of the dangerous cases are already handled:

| Input to a required string field | Result |
|---|---|
| a real null (`None`, `NaN`, `pd.NA`) | **refused** |
| empty string `""` | **refused** by the minimum-length check |
| a null written to TSV and read back | **refused** — writes as empty, reads back as empty or null |
| `" "` (whitespace only) | **accepted** |
| `"NA"`, `"None"`, `"nan"`, `"null"`, `"-"`, `"."` | **accepted** |

The round-trip being clean is the good news, and it is why this is latent rather than live: our own
writes cannot produce it.

## The path that could produce it

An upstream source file containing a literal missing-value marker. That is ordinary in biological
data — `NA`, `N/A`, `-` and `.` are all conventional in published supplementary tables and exports.

Fourteen places in the codebase read with `keep_default_na=False`, which is **correct** and should
stay: it is what stops pandas mangling values and what protects numeric precision. But it also means
a literal `NA` in an upstream column arrives as the three-character string `NA` and is then a
perfectly good non-empty string as far as the schema is concerned.

So a required cohort identifier, source record identifier, reviewer or citation could be the word
for "missing" and validate.

## Why this is the same class of problem as #323

`AGENTS.md` is explicit: *"Never turn uncertainty or missingness into plausible metadata. Do not
invent or default a coordinate, radius, population identity, sample/cohort ID, assay, sampling
design, disease ascertainment, date, denominator, count, allele orientation, citation, source
locator, reviewer, or reuse check."*

A stored `"NA"` is indistinguishable from a recorded identity once it is in the store, exactly as a
truncated `200` was indistinguishable from a measured one. The schema has designated states for
absence — `not_reviewed`, `not_reported`, `ambiguous`, `not_checked` — and the point of them is that
a reader can tell the difference. A literal `NA` defeats that silently.

## Verified, not assumed

- No schema-validated required string column in `data/registry`, `data/observations` or
  `tests/fixtures` currently holds one of these. 35 files, 73 required non-empty string columns
  across all schemas, zero hits.
- Plenty exist in raw acquisition inputs under `data/research/`, which is correct — a source file
  should be preserved as received, not rewritten.

## Suggested fix, and the decision inside it

Add the check to the existing guard in `tests/test_schema_coercion_guard.py`, which already walks
every schema behaviourally.

The decision that needs making first: **which literals count.** `"NA"` and `"None"` are clearly
markers. `"-"` and `"."` are less obvious, and `"."` in particular is a legitimate value in some
genomic formats, where it is VCF's own missing marker but also appears in real identifiers. Getting
this wrong in the strict direction would reject valid data, which is worse than the gap.

My suggestion is to start strict on the unambiguous set and on whitespace-only, and leave the
punctuation markers out until someone can point at a column where they would matter:

```
"" (already refused), whitespace-only, "NA", "N/A", "None", "nan", "NaN", "null", "NULL"
```

and to apply it only to required non-nullable string columns, since a nullable column has a real way
to say "absent" already.
