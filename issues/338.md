## Body

## TL;DR

#323 fixed a real bug: our observation schemas were silently rounding fractional counts down instead
of rejecting them, so a measurement of "200.5 people" quietly became 200 and nothing downstream
could tell it had been invented.

The same bug is still live in the curated registry, in three columns that count things. #323 was
right not to widen its scope; this is the rest of it.

---

## Confirmed, not inferred

`CPIC_COVERAGE_SCHEMA` in `genomeos/registry/curated.py` declares three columns as plain `int` in a
schema with `coerce=True`. Pandera coerces before it checks, and numpy integer casting truncates, so:

```
pair_count=3.9         -> ACCEPTED, stored as 3
allele_row_count=10.7  -> ACCEPTED, stored as 10
candidate_count=2.5    -> ACCEPTED, stored as 2
```

Verified against a complete, otherwise-valid row. These are the identical shape #323 removed from
`OBSERVATIONS_SCHEMA` and `CARRIER_OBSERVATIONS_SCHEMA`.

## Why it matters less here, and still matters

Nothing feeds these three from a floating-point computation today, so unlike the observations case
there is no known live path that produces a fraction. That is why this is a follow-up and not a bug
report.

But the reason #323 was worth doing is not that a fraction had been seen. It is that **a coerced
value is indistinguishable from a measured one once stored**, and §12 says a bad value fails the
build rather than being quietly repaired. A count of anything is either a whole number or a mistake.
Leaving three of them able to absorb a fraction leaves the same trap set, in a schema that gates
what reaches the curated variant set.

## The fix

Exactly what #323 did: change the three to pandas' nullable `Int64`, whose casting raises on a
non-integral value while still accepting an integral float like `3.0`. Then re-freeze the contract
and commit the diff.

Worth reading #323's comment in `genomeos/observations/schema.py` first — it records why
column-level `coerce=False` cannot help, since schema-level coercion wins, and why global
`coerce=False` was rejected.

## Worth checking at the same time

I grepped for other columns with this shape and these three were the only ones left. That is a grep,
not a proof. The schemas in `genomeos/registry/schema.py`, `genomeos/registry/variants.py` and
`genomeos/observations/evidence.py` all set `coerce=True`, and any integer-typed column added to them
later inherits the same behaviour.

A cheap way to make this not recur: a test that walks every declared schema and asserts no column is
a plain numpy integer type. That turns "we grepped once" into something the build enforces.

Found while reviewing #323, which closes #192.
