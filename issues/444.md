## Body

## Problem

Until the f64 detail tier loads, hover and the inspector show only the cell id, the support label and "Loading cell values…". The render tier, already loaded, has `post_mean` and `post_sd` as f32. At the readout's precision (percent, 2 decimals) those match the f64 values in every cell of all 30 datasets except one `post_sd`, and that one differs only in the last digit.

## Change

Before the detail tier arrives, show mean and SD from the render tier, visibly marked as provisional: an "≈" prefix plus an accessible "approximate; exact value loading" label. The 95% interval and the distance to the nearest observation, which only the detail tier has, show "Loading…". When the detail tier arrives, swap in the exact values.

Constraints:
- Exact (unmarked) numbers come only from the detail tier, so every number shown as exact stays bit-identical to the citable artifact.
- If the detail tier fails, keep the provisional values and the existing "Cell values unavailable" retry.

## Acceptance

- Spec §B.2 is amended so render values may be displayed only as marked provisional numbers.
- The type separation between `renderAt` and `cellAt` is kept: a provisional value can't be formatted as exact.
- Unit and component tests cover the provisional, exact and failed states.
- An e2e test hovers before the detail tier loads and sees the ≈ values.

### bschilder, 2026-10-13T18:04:30Z (https://github.com/genomeOS/genomeOS/issues/444#issuecomment-6151955931)

**Correction to the precision figure above.** The implementation measured the gap between f32 and f64 across every value the readout can show. It covered all 30 published surfaces, at 77,844 cells per surface, for `post_mean` and `post_sd`: 4,670,640 readouts in all. Each value was formatted the way the site does it, `(v*100).toFixed(2)`.

- **77 readouts differ,** not one. Each is off by exactly one unit in the last digit (0.01 percentage points).
- **The largest raw f32 error is 2.98e-6 percentage points.** The differences are all rounding at the second decimal.
- **The "one `post_sd`" figure came from a different check.** It counted the one value whose f32 rounding crosses a display-bin edge (`cyt-il-10-819-t` `post_sd`), not readouts that differ.

The design still holds. This is why the provisional values carry the ≈ marker until the f64 detail tier arrives. The corrected figure is recorded in the fast-load spec (§B.2) on the branch for this issue.
