## Body

## TL;DR

Timing-sensitive marketing-site e2e tests fail intermittently in the `pages` workflow. Each run fails a different one, on code that has not changed. This blocks unrelated PRs and forces re-runs.

## Evidence

PR #474 changes no file under `website/`, and its website tree and `pages.yml` are byte-identical to an earlier commit of the same PR whose shard passed. Yet:

| Run / attempt | Failed (after Playwright's 2 retries) | Marked flaky |
|---|---|---|
| 39048043669, attempt 1, e2e shard 1/4 | `marketing-home.spec.ts:1126`: the "How it works" scroll position (`expect.poll(...).toBe(true)`, received `false`) | none |
| 39048043669, attempt 2, same shard | `marketing-home.spec.ts:569`: the steps plate Replay (`data-scene-state` received `"playing"`, expected `"rest"`) | `marketing-contact.spec.ts:629` (hint at 1.5 s), `marketing-home.spec.ts:531` (steps play once at 35%) |
| 38840790201 (feat/site-redesign) | `marketing-projects.spec.ts:1739`: the recolour takes at most 300 ms | none |
| 38756359170 (feat/site-redesign) | `marketing-contact.spec.ts:2656`: glyph alignment before and after joining | none |

Every one of these tests asserts an animation state, a scroll position or a wall-clock duration on a shared CI runner.

## Ask

Make these tests deterministic. Possible approaches:

- drive animations to a known state (reduced motion, or an explicit test hook) instead of waiting on wall-clock time;
- widen tolerances where the claim allows it;
- quarantine and track a test until it is fixed.

`pages` is not a required check on `main` today, but a red run still obscures real failures.
